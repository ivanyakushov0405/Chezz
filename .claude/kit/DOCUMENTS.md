# Документы основ проекта

`/setup` превращает ТЗ и ограничения бизнеса в документы-основы, а из них собирает конвейер под проект. Файл одинаков для любого проекта. Агенты читают его **разделами** (`.claude/kit/scripts/section.sh .claude/kit/DOCUMENTS.md --title "<заголовок>"`).

## Входы
| Файл | Что это | Обязателен |
|---|---|---|
| `docs/TZ.md` | ТЗ в markdown с сохранённой нумерацией разделов (`### 3.4.2. …`) | да |
| `docs/setup/BUSINESS.md` | ограничения бизнеса: нагрузка (пользователи онлайн в пике, запросы в секунду, объём данных, рост за 12 месяцев), команда, бюджет, сроки, кто утверждает, стек, запреты, трекер, инструменты, что вне этапа. **Заполняется только по ТЗ** (автор, режим `business`): каждое значение со ссылкой «ТЗ §N.N»; чего нет в ТЗ — помеченное допущение | да — `/setup` создаст сам |
| существующие документы | если проект не с нуля | нет |

## Документы — строго в этом порядке
Каждый следующий опирается на утверждённые предыдущие. Документ может быть разделом другого файла; тогда в профиле указывается файл и раздел. Ненужный проекту документ пропускается с причиной в BUSINESS.md («Вне этапа»).

| # | Документ | Файл по умолчанию | Что фиксирует | Критики |
|---|---|---|---|---|
| F1 | Глоссарий и модель домена | `docs/GLOSSARY.md` | сущности, роли, термины, связи; имя термина в коде и в интерфейсе | tz, consistency |
| F2 | Архитектура | `docs/ARCHITECTURE.md` | приложения, модули или сервисы, слои и разрешённые зависимости, процессы, владение данными, внешние компоненты, ADR; **каждое крупное решение обосновано цифрами BUSINESS.md**, у решений «по умолчанию» — более простая альтернатива и план роста | tz, proportionality, consistency, agentability |
| F3 | Безопасность и данные | `docs/SECURITY.md` | угрозы, аутентификация и сессии, права, персональные данные, хранение и удаление, логи, доступ сотрудников, секреты | security, tz, proportionality |
| F4 | API-конвенции | `docs/API_CONVENTIONS.md` | транспорт, формат, ошибки, пагинация, версии, realtime, межмодульное взаимодействие, каталог эндпоинтов | tz, security, consistency, agentability |
| F5 | Дизайн-система | `docs/DESIGN_SYSTEM.md` | токены и их уровни, темы, целевые экраны, состояния, доступность, связь с макетами | tz, agentability |
| F6 | Стратегия тестирования и DoD | `docs/TESTING.md` | кто какие тесты пишет, уровни и места, тестовая инфраструктура, что в задаче и что в CI, Definition of Done | agentability, consistency |
| F7 | Эксплуатация и DevOps | `docs/OPERATIONS.md` | среды и их назначение, инфраструктура как код, CI (стадии и обязательные проверки), выкатка (staging, smoke, прод, откат) — **только через CI-workflow**, секреты сред — только в CI (локальной машине и агентам доступ к staging и проду не нужен), наблюдаемость и алерты, бэкапы и проверка восстановления, кто и что может в проде | tz, security, proportionality, agentability |
| F8 | Конвейер | `.claude/profile.md`, `.claude/zones.conf`, `.claude/agents/*`, `CLAUDE.md` ×N, `docs/PIPELINE_DECISIONS.md` | роли и зоны, метки задач, проверки, трекер, модели, правила для агентов | roster, agentability, consistency |

## Обязательная часть каждого документа F1–F7
- статус и версия;
- таблица решений: номер, решение, источник — **ТЗ** (со ссылкой), **бизнес**, **по умолчанию**, **ревью**; у «по умолчанию» — более простая альтернатива и почему не она;
- ссылки на ТЗ в виде `ТЗ §N.N` — по ним считается покрытие;
- MUST / MUST NOT для правил, которые агенты обязаны соблюдать;
- примеры **из домена проекта**;
- короткие нумерованные разделы: неделимый раздел ≤ ≈1500 токенов — агент читает раздел, а не файл;
- открытые вопросы с владельцем.

## Линзы критиков
Рубрики — в `.claude/kit/lenses/<линза>.md`; критик читает только свою. Модель — для вызова из `/setup`.

| Линза | Вопрос | Модель |
|---|---|---|
| `tz` | Документ соответствует ТЗ и бизнесу? | opus |
| `security` | Где можно навредить? | opus |
| `proportionality` | Соразмерно ли решение нагрузке, команде и бюджету? Можно ли проще? | opus |
| `roster` | Хватает ли ролей, нет ли лишних, у каждой работы есть исполнитель и проверяющий? | opus |
| `consistency` | Документ согласован сам с собой и с остальными? | sonnet |
| `agentability` | Агент сможет работать по нему без догадок и без лишних токенов? | sonnet |

## Цикл «автор → критики»
1. Автор пишет черновик или принимает существующий документ.
2. Критики линз документа работают **параллельно**; отчёт — `docs/setup/reviews/<F#>-<линза>-r<раунд>.md`.
3. Важность: 🔴 блокер, 🟠 важно, 🟡 доработка. **Блокируют только 🔴.**
4. Автор отвечает на каждую находку (принято / отклонено с обоснованием / человеку) — `docs/setup/reviews/<F#>-response-r<раунд>.md`.
5. Следующий раунд — только линзы, где были 🔴, и только по изменённым разделам. **Изменённые разделы определяет git** (`section.sh --changed`), а не автор. Не больше **3 раундов**; оставшиеся 🔴 решает человек.
5а. Если документ менялся после раунда 1 — перед утверждением `consistency` читает его **целиком** один раз.
6. ⛔ Человек утверждает документ. Отклонённые автором 🔴 он видит отдельным списком.
7. Утверждённый документ можно **переоткрыть** (`/setup reopen F<N>`): новая критика его и каскадная проверка документов, которые на него опираются.

## Экономия токенов — правила для всех агентов набора
1. Большие файлы — только разделами: `section.sh <файл> <номер> --with-refs` (подтягивает разделы, на которые ссылается прочитанный) или `--title "<текст>"`; оглавление — `section.sh --toc <файл> 3`. Read целиком — только для файлов меньше ≈2000 токенов.
2. Ответ оркестратору — коротко (обычно ≤ 10 строк); подробности — в файлах артефактов.
3. Повторные проверки — по изменениям: критик в раунде > 1 и ревьюер в итерации > 1 смотрят только изменённое и прошлые замечания.
4. Правила в агентах — ссылками на разделы документов, а не копиями. Сгенерированный агент ≤ ≈1500 токенов (`token-report.sh`).
5. Сильная модель — для решений и независимых проверок; механическая работа и прогоны — обычная модель или скрипт.
6. Механические проверки — скриптами, не агентами: зоны (`check-zone.sh`), покрытие ТЗ (`tz-coverage.sh`), стоимость (`token-report.sh`).
