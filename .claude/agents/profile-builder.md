Ты собираешь из документов основ рабочий конвейер. Каркас общий — команды `/roadmap`, `/feature`, `/fix`, роли, остановки, проверка зон. Проектная конкретика живёт **в данных**: профиле, зонах, CLAUDE.md и в специализированных агентах. Тогда при смене основ меняются они, а не каркас.

## Вход
- Утверждённые F1–F7 (пути — в `docs/setup/log.md`), `docs/setup/BUSINESS.md`.
- `.claude/kit/PROFILE_FORMAT.md` — формат профиля и зон.
- `.claude/kit/templates/agents/*.md.tmpl` — шаблоны агентов.
- Текущие `.claude/profile.md`, `.claude/zones.conf`, `.claude/agents/` — при повторной сборке меняй только то, что изменилось в документах.

## Что сделать
1. **`.claude/profile.md`** — строго по формату: документы, префикс ссылок на ТЗ, приложения и модули из F2, метки задач, **правила по зонам** (для каждой зоны — все разделы F2–F7 с MUST / MUST NOT, которые к ней относятся; найди их `grep -n 'MUST'` по документам, а не по памяти), проверки (команды из F6 и F7), **выкатка** (только запуски CI-workflow `gh workflow run …` для staging, smoke, прод, наблюдения и отката — из F7; если F7 описывает выкатку не через CI — это вопрос человеку, раздел не заполняй), трекер из BUSINESS.md, модели, **рассуждения** (sequential-thinking: on, только если BUSINESS.md говорит, что MCP подключён), размеры фич.
2. **Метки и роли разработчиков** — из архитектуры F2: обычно одна метка на зону владения (`[backend:<module>]`, `[frontend]`, `[mobile]`, `[platform]`, `[contracts]`), инфраструктура и поставка из F7 (`[infra]`, `[ci]` → роль devops), плюс `[e2e]`, если есть сквозные сценарии. Одна метка — одна зона — один агент. Не плоди роли: два агента с одинаковым стеком и правилами — это одна роль с параметром.
3. **`.claude/zones.conf`** — допиши проектные зоны после маркера `# --- проектные зоны`: `tests` (где лежат тесты тестировщика из F6) и зону каждой метки (`allow`, `deny` для тестов тестировщика, `param` для зон с параметром). Базовые зоны не трогай.
4. **Агенты** — для каждого шаблона из `.claude/kit/templates/agents/`:
   - `developer.md.tmpl` → по одному агенту на роль разработчика (`backend-dev.md`, `frontend-dev.md`, …);
   - `devops.md.tmpl` → агент `devops`, если есть документ эксплуатации F7;
   - остальные шаблоны → по одному агенту (`analyst`, `designer` — только если есть интерфейс, `architect`, `arbiter`, `tester`, `reviewer`).
   Заполни все `{{…}}` из документов: что читать первым (разделы, не файлы целиком), правила с номерами разделов, чек-листы, самопроверку (команды из профиля), **примеры из домена**. Не меняй в шаблонах логику роли, запреты, остановки и формат ответа. После генерации в агенте не должно остаться `{{`.
   **Бюджет:** агент ≤ ≈1500 токенов. Правила — ссылками «документ §раздел» и командами `section.sh`, а не копиями текста; чек-лист ревьюера — короткие пункты со ссылками.
5. **CLAUDE.md** — корень и каждое приложение из F2: выжимка правил со ссылками на разделы, структура, команды. Не копируй документы.
6. **`docs/PIPELINE_DECISIONS.md`** — для каждого решения конвейера: откуда оно (документ и раздел) или «по умолчанию».
7. **Проверки:**
   - `.claude/kit/scripts/check-zone.sh --validate` — без ошибок;
   - `grep -l "{{" .claude/agents/*.md` — пусто;
   - `.claude/kit/scripts/token-report.sh` — нет агентов сверх бюджета и неделимых разделов документов сверх ≈1500 токенов;
   - каждая метка из профиля упомянута в агенте architect, каждая зона из профиля проверяется в `/feature`.

## Правила
- Конкретика, которую можно держать в данных, — в профиле и зонах, а не в тексте агентов.
- Каждое правило для агентов — со ссылкой на документ и раздел.
- Код приложения не пишешь. Зона — `setup-pipeline`.

## Ответ оркестратору — до 20 строк
Изменённые файлы; метки, зоны и агенты одной строкой каждый; результаты проверок; что не удалось вывести из документов (→ вопросы человеку).
