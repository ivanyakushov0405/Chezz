## 1. Правила для агентов

- MUST: бэкенд — один процесс `app` в каждой среде (модульный монолит, раздел 7). Новый сервис, воркер, контейнер или `cluster`/`worker_threads` — только через правку этого документа.
- MUST: имена сущностей, полей и значений — из `docs/GLOSSARY.md`. TS-типы называются как в колонке «Код» глоссария (`Game`, `Challenge`, `Seek`), поля — как в глоссарии (`time_base`, `white_id`), A23.
- MUST: модуль обращается к другому модулю только через его `service` (вызовы) или `events` (подписка), только по таблице 7.1, не к его таблицам и `repo`. Проверяют `dependency-cruiser` и `scripts/check-architecture.sh` в CI (раздел 7.4).
- MUST: ход, часы и окончание партии решает только сервер (ТЗ §4.6, §5). Клиент показывает то, что прислал сервер (раздел 10).
- MUST: ход и, если он закончил партию, её итог сохраняются в PostgreSQL одной транзакцией **до** рассылки (ТЗ §5, раздел 9.2).
- MUST: типы и схемы сообщений REST и WebSocket — только в `packages/protocol` (A14); правила шахмат — только через `packages/chess` (A3).
- MUST NOT: синхронные тяжёлые операции в обработчиках и комнатах партий (синхронный `fs`, циклы по всем партиям, `JSON.stringify` всей истории на каждый ход) — они задерживают ходы всех партий (раздел 9.4).
- MUST NOT: добавлять Redis, очереди сообщений, второй экземпляр `app` в среде, отдельный SSR-сервер — до признака из раздела 15.
- MUST NOT: вводить модули, таблицы и эндпоинты для того, что вне этапа: жалобы, админ-панель, бан, аннулирование, дашборд (BUSINESS §1.7, GLOSSARY §3).
- MUST NOT: считать разбор Stockfish на сервере (ТЗ §4.9, §6).

## 4. Стек

### 4.1. Бэкенд: выбор человека

Решение человека (Ivan, утверждение F2, 2026-11-04): Node.js + TypeScript. Сравнение, по которому оно принято:

| Критерий | Node.js + TS (выбран) | Rust (отвергнут) | Go |
|---|---|---|---|
| Один разработчик | Один язык с фронтендом, общие пакеты | Второй язык, async Rust, сборка минутами | Второй язык |
| Совпадение правил с клиентом | Та же chess.js — по построению | Другой движок + сверка | Другой движок + сверка |
| Типы протокола | Общий пакет | Генерация | Генерация |
| Память на процесс | ≈ 80–150 МБ | ≈ 10–30 МБ | ≈ 20–40 МБ |
| p95 ≤ 150 мс при ≤ 100 сообщениях/с | С запасом | С запасом | С запасом |

Разница в памяти — ≈ 0,1 ГБ на среду из 4 ГБ, размер VPS не меняет. Риск Node.js — один поток: долгая синхронная операция задерживает ходы всех партий. Меры — раздел 9.4.

Пакеты сервера (по умолчанию): `fastify`, `@fastify/websocket`, `@fastify/rate-limit`, `@fastify/static`, `kysely`, `pg`, `zod`, `chess.js` (через `packages/chess`), `pino`, `prom-client`, `@sentry/node`. Проверка Google ID-токена и библиотека OIDC — F3. Тесты — F6.

### 4.2. Фронтенд

React + TypeScript (ТЗ §6), Vite, SPA; публичные страницы получают серверный HTML для поисковиков от модуля `seo` (A5, раздел 12.1). Доска — chessground, правила — `packages/chess`, разбор — Stockfish WASM в Web Worker (A6), типы и схемы — `packages/protocol`. Переводы RU/EN — файлы переводов (ТЗ §5), библиотеку выбирает F5. Подробности — раздел 12.

## 5. Процессы и среды

Один VPS, Docker Compose (BUSINESS D6).

| Контейнер | Что делает | Где |
|---|---|---|
| `edge` | Caddy: HTTPS (Let's Encrypt), маршрут по домену в `app` нужной среды | общий |
| `app` | Node.js: REST, WebSocket, комнаты партий, цикл подбора, истечение вызовов, кэш лидеров, статика SPA, HTML публичных страниц и `sitemap.xml` (модуль `seo`), `/metrics` | prod; staging — по требованию |
| `db` | PostgreSQL | prod; staging — по требованию, одноразовая |

- Образ `app` содержит сервер и собранный фронтенд: клиент и сервер выкатываются одной версией, `packages/protocol` у них общий.
- Бэкап БД prod (ТЗ §5) — задача по расписанию на VPS (`pg_dump`); место копий и проверку восстановления задаёт F7. Staging не бэкапится (A17).
- Ориентир VPS (по умолчанию): 2 vCPU / 4 ГБ RAM. prod: `app` ≤ 200 МБ, `db` ≤ 512 МБ, `edge` ≈ 50 МБ; со staging — около 1,5 ГБ. Остальное — кэш ОС и запас на нагрузочный тест. 2 ГБ — допустимо, но без запаса на тест.
- Нагрузочный тест (ТЗ §7, этап 5) — на staging, в часы без игроков; где запускается генератор нагрузки — F6, F7.
- Выкатка: перезапуск `app` — секунды; клиенты переподключаются, таймер переподключения 60 с (ТЗ §4.6) покрывает перерыв, партии восстанавливаются (9.3). Считать ли выкатку плановой работой с объявлением за 24 ч (ТЗ §5) и окна выкатки — F7. Выкатка — только через CI (F7).
- MUST: миграции только добавляющие (новые таблицы, поля с default); откат = предыдущий образ на той же схеме. Удаление, переименование, смену типа ловит `scripts/check-architecture.sh` (7.4).

### 6.2. Нужен ли Redis

ТЗ §6 рекомендует Redis для пяти задач. При одном процессе `app` каждая решается без него:

| Задача из ТЗ §6 | Решение без Redis | Почему достаточно |
|---|---|---|
| Очередь подбора | Seek в памяти, проход раз в 1 с | ≤ 150 заявок — перебор пар мгновенный |
| Онлайн-статусы | Реестр WebSocket-подключений | ≤ 150 записей |
| Состояние часов | `GameRoom` + запись в PostgreSQL после каждого хода | ТЗ §5 требует надёжности; Redis без fsync её не даёт, с fsync — дублирует PostgreSQL |
| pub/sub | `events` модулей в процессе (раздел 7.3) | Между машинами нужен только при нескольких процессах |
| Кэш лидеров | Кэш в памяти на 5 мин | Запрос по ≤ 9 000 строк Rating — миллисекунды |

Нагрузка на PostgreSQL: ≤ 100 записей ходов в секунду (BUSINESS D2) — малые транзакции одной-двух строк, с большим запасом.

Итог: Redis не нужен (A8). Когда он появится — раздел 15.

| `games` | Game, Move, часы, `GameRoom`, зрители, «1 активная партия» (A25), снимок состояния | `rating`, `users` | §4.6 |

| `matchmaking` | Seek, окно поиска, чередование цветов, «не больше 3 раз подряд», предложение вызова через 60 с | `games`, `rating`, `users` | §4.4 |
| `profile` | сборка профиля: статистика, график, последние партии (только чтение) | `users`, `games`, `rating` | §4.2 |

- От `platform` и `analytics` может зависеть любой модуль; от `packages/protocol` и `packages/chess` — любой. Остальные связи — только из таблицы; граф без циклов.
- MUST NOT: обратные зависимости — `games` не знает о `challenges`, `matchmaking`, `realtime`, `profile`, `seo`; `users` и `feedback` ни от кого; от `seo` не зависит никто.
- Что именно обезличивается при удалении аккаунта — F3 (GLOSSARY Q6).

### 7.2. Слои внутри модуля

```
api.ts      — маршруты Fastify и обработчики сообщений WebSocket
service.ts  — сценарии; публичный интерфейс для других модулей
events.ts   — EventEmitter модуля с типизированными событиями (если есть), 7.3
domain/     — чистая логика без ввода-вывода (часы, Glicko-2, окно подбора)
repo.ts     — запросы Kysely к таблицам своего модуля
```

- MUST: `api` → `service` → `domain` и `repo`. `domain` импортирует только `packages/chess` и собственный код; время передаётся параметром.
- MUST NOT: `api` импортирует `repo`; `domain` импортирует `kysely`, `pg`, `fastify`, `ws` или вызывает `Date.now()`, `performance.now()`, `new Date()` без аргумента.
- Модуль без своей логики (`feedback`, `auth`, `profile`, `analytics`, `seo`) может обходиться без `domain`; запрет `api` → `repo` действует всегда.
- Транзакция на несколько модулей открывается в `service` того модуля, который начинает сценарий, и передаётся в `service` других модулей параметром (`trx`). Каждый модуль внутри неё пишет только в свои таблицы через свой `repo`.

### 7.3. События между модулями

Модуль сообщает о событиях через свой `events.ts`; подписчик зависит от модуля-издателя по таблице 7.1, издатель о подписчиках не знает. Обработчики событий не бросают исключений наружу и не блокируют издателя.

| Издатель | События (примеры) | Подписчики |
|---|---|---|
| `games` | партия началась (`game_id`, `white_id`, `black_id`); ход; партия закончилась | `realtime`, `matchmaking` (снять Seek игроков) |
| `challenges` | вызов создан, принят, отменён, истёк (лобби) | `realtime` |
| `matchmaking` | заявка создана; 60 с без соперника — предложить вызов (ТЗ §4.4 п.3) | `realtime` |

- Пример: подбор свёл две заявки 3+2 → `matchmaking` вызывает `games.service.createGame` → `games` создаёт Game, `GameRoom` и публикует «партия началась» → `realtime` по `white_id` и `black_id` находит подключения, шлёт событие и подписывает их на партию; `matchmaking` снимает Seek обоих.
- Если `createGame` отказал «игрок занят»: Seek занятого игрока снимается, Seek второго остаётся в очереди с прежним временем старта.
- Форма сообщений клиенту — F4.

Правка 7.1 → правка конфига в той же задаче.
- `scripts/check-architecture.sh`: Kysely-запросы (`selectFrom`, `insertInto`, `updateTable`, `deleteFrom`, `sql\``) — только в `*/repo.ts` и в `apps/server/migrations/`; таблица в запросах `repo.ts` — только своего модуля (по таблице 8); `Date.now`, `performance.now`, `new Date()` — не в `domain/`; в `migrations/` нет `dropTable`, `dropColumn`, `renameColumn`, `renameTo`, `setDataType` и их SQL-аналогов.

### 7.5. Аналитика (ТЗ §5, §7)

- Событие — строка `analytics_events`: `id`, `name`, `user_id` (может быть пуст), `game_id` (может быть пуст), `props` (jsonb), `created_at`. Техническая запись, как строка лога: в интерфейсе её нет, сущностью домена она не является (F2-Q7).
- Имена событий: `user_registered`; `user_active` — не больше одного на User в сутки (UTC), при первом REST-запросе или открытии WebSocket с действующей Session; `seek_started`; `seek_matched` и `seek_cancelled` (`props.wait_ms`); `game_started` и `game_finished` (`props.termination`, `props.after_restart`) — **по строке на каждого игрока**, обе с `game_id`; `analysis_opened` (с клиента, через REST — форма F4).
- `user_active`: отметка «уже записан сегодня» — в памяти; после перезапуска возможен дубль, на подсчёт разных `user_id` он не влияет.
- Метрики ТЗ §7 — SQL-запросы:
  - DAU — число разных `user_id` в `user_active` за сутки. Гость без сессии в DAU не входит (по умолчанию);
  - среднее время ожидания подбора — среднее `seek_matched.wait_ms`; отменённые заявки (`seek_cancelled`) в цель «≤ 20 с» не входят, но хранятся для анализа (по умолчанию);
  - доля партий, прерванных из-за сбоев, — партии с `game_finished.after_restart = true` от всех законченных за период (флаг ставится по 9.3);
  - удержание на 7-й день и «новичок сыграл партию в первый день» — `user_registered` + `game_started` по `user_id`.
- MUST: запись события не блокирует и не ломает сценарий: ошибка записи логируется, ход и партия идут дальше.
- MUST NOT: класть в `props` e-mail, имя из Google, IP. Что считать ПДн в событиях и срок хранения — F3.

## 9. Партия: комната, часы, сохранение

### 9.1. Жизненный цикл

1. Создание — только `games.service.createGame(trx, …)`. В транзакции: `users.service.lockForGame(trx, [white_id, black_id])` (`SELECT … FOR UPDATE` в `users/repo.ts`, по возрастанию `id`) → отказ «игрок занят», если у кого-то есть `active` Game (A25) → вставка Game со `status = active`. После коммита — `GameRoom` и событие «партия началась» (7.3).
2. Принятие вызова: `challenges.service.accept` открывает транзакцию, вызывает `games.service.createGame(trx, …)` и в той же транзакции ставит `Challenge.status = accepted` через свой `repo`. Подбор: `matchmaking.service` открывает транзакцию и вызывает `createGame`.
3. «1 открытый вызов»: частичный уникальный индекс `challenges(creator_id) WHERE status = 'open'`. Открытый вызов игрока, который сейчас в партии, остаётся в лобби; его принятие отклоняется («игрок занят»).
4. Команды `GameRoom`: ход, сдаться, ничья (предложить / принять / отклонить), возврат хода, отмена, подключение / отключение, выбор после разрыва (GLOSSARY G21), срабатывание таймера.
5. При подключении игрока или зрителя (в том числе после перезагрузки страницы, ТЗ §7) комната шлёт полный снимок: ходы, остатки обоих часов, чей ход, открытые предложения, идущие таймеры. Форма — F4.
6. Таймеры (`setTimeout`, при срабатывании ставят команду в очередь комнаты): флаг; первый ход 30 с (`no_first_move`); переподключение 60 с, не больше остатка; окно выбора 30 с (G21).
7. Конец партии (ход, таймер, команда) — одна транзакция: Game (`status`, `result`, `termination`, `pgn`, `ended_at`) и, если партия рейтинговая и `finished`, `rating.service.applyResult(trx, …)`. Потом рассылка, событие «партия закончилась», `game_finished` в аналитику, комната удаляется из памяти.
8. Флаг: если у соперника недостаточно материала для мата (`packages/chess`) — `draw` + `timeout_insufficient_material`, иначе победа соперника + `timeout` (ТЗ §4.6, GLOSSARY §8).

### 9.2. Ход

Команды одной комнаты выполняются строго по очереди: следующая начинается после завершения предыдущей, включая запись в БД (A9).

1. Проверить ход через `packages/chess` (ТЗ §4.6).
2. Часы: `затрачено = сейчас − начало хода − компенсация` (A11, ≤ 1 с), время — монотонное (`performance.now()` в `service`, в `domain` — параметром); вычесть из остатка; ≤ 0 — флаг (9.1 п.8); иначе прибавить `time_increment`.
3. Проверить окончание: мат, пат, недостаток материала, троекратное повторение, 50 ходов — автоматически (ТЗ §4.6).
4. Сохранить одной транзакцией: `moves = moves || <Move>` (Move = SAN + остаток часов, GLOSSARY §8) и, если партия закончилась, итог по 9.1 п.7.
5. После коммита — разослать ход (и итог) игрокам и зрителям с остатками обоих часов.

- Пример: блиц 3+2, у белых 2:41,300, думали 4,2 с, RTT 160 мс → компенсация 80 мс → затрачено 4,12 с → 2:37,180 + 2 с = 2:39,180 в Move.
- MUST: клиент получает остатки часов в каждом сообщении о ходе и только отображает их (ТЗ §4.6, §7 «≤ 0,5 с»).
- Время на ход для разбора (ТЗ §4.9) выводится из соседних остатков и добавки; компенсация не хранится, точность — до 1 с. Хватает ли — F4, F5.

### 9.3. Восстановление после перезапуска

При старте `app` читает Game со `status = active` и создаёт комнаты:
- позиция — из `moves[]`; остатки — из последнего Move каждой стороны или `time_base`;
- сторона, чей ход, получает время на начало своего хода (A10, решение человека);
- в партии без ходов таймер первого хода начинается заново;
- оба игрока считаются отключёнными: у каждого идёт таймер переподключения 60 с, помеченный «после перезапуска»;
- открытые предложения ничьей и возврата хода и незавершённое окно выбора сбрасываются;
- не вернулись оба — `aborted` + `abandonment`, рейтинг не меняется (человек, утверждение F2, 2026-11-04); вернулся один — ему окно выбора по G21;
- `props.after_restart = true` ставится, только если партия закончилась по истечении таймера переподключения, помеченного «после перезапуска». Игрок вернулся, а потом ушёл сам — флага нет.

Итог хода не теряется: он записан вместе с ходом (9.2 п.4).

### 9.4. Один поток и задержка хода

- Обработка хода — доли миллисекунды CPU; p95 ≤ 150 мс определяют сеть и коммит PostgreSQL (единицы мс).
- MUST: метрика задержки event loop (`monitorEventLoopDelay`) в `/metrics` (A22); p99 > 50 мс — признак раздела 15.
- MUST NOT: тяжёлое в обработчиках (раздел 1). Сборка `pgn` — один раз в конце партии; запрос таблицы лидеров — асинхронный, раз в 5 мин.

## 10. Правила шахмат

- MUST: сервер — единственный источник правды о допустимости хода, SAN и окончании. Сервер и клиент используют один `packages/chess` (обёртка chess.js, A3).
- `packages/chess` содержит: применение хода, SAN, проверку окончаний через chess.js (`isCheckmate`, `isStalemate`, `isInsufficientMaterial`, `isThreefoldRepetition`, правило 50 ходов) и свою функцию «может ли сторона поставить мат» для флага (9.1 п.8).
- MUST: клиент использует пакет для подсказок (подсветка ходов, превращение) и разбора; SAN в нотации берётся из сообщения сервера.
- MUST NOT: клиент сам объявляет мат, пат или ничью.
- MUST: `fixtures/chess/*.json` — FEN, допустимые ходы (UCI), SAN каждого хода, ожидаемое окончание; прогоняются тестами `packages/chess` в CI. Обязательные случаи: рокировка, взятие на проходе, превращение, пат, троекратное повторение, 50 ходов, недостаток материала, флаг при недостатке материала у соперника (ТЗ §7).
- Пример фикстуры: взятие на проходе `e5d6` → SAN `exd6`; флаг белых, у чёрных король и конь → `draw`, `timeout_insufficient_material`.
- Ход, отклонённый сервером (например, пришёл после флага), → клиент возвращает фигуру и показывает позицию сервера.

## 11. Рейтинг и таблица лидеров

- `rating/domain/glicko2.ts` — чистая функция: (рейтинг, RD, волатильность обоих, результат, время с последней партии) → новые значения. Параметры ТЗ §4.7: 1500, RD 350, 0,06, τ = 0,5; пересчёт сразу после партии, без периодов (метод Lichess).
- MUST: эталонные векторы в `fixtures/glicko2/`: численный пример из статьи Glickman «Example of the Glicko-2 system» и случаи из реализации Glicko-2 в репозитории `lichess-org/lila` (модуль `rating`). Если подходящих случаев там нет — набор, посчитанный вручную по формулам статьи. Форма файлов — F6.
- `applyResult` пишет Rating обоих и две строки RatingHistory в транзакции конца партии (9.1 п.7).
- Таблица лидеров: `ratings` (RD ≤ 110) и `rating_history` (партия за 14 дней, изменение за 7 дней), топ-100 по категории, кэш 5 мин (ТЗ §4.8, GLOSSARY G27). «Ваше место» — отдельный запрос, вне кэша.

## 12. Фронтенд

- SPA (A5): `app` отдаёт `index.html` и статику (`@fastify/static`); маршрутизация на клиенте. Для публичных маршрутов `index.html` дополняет модуль `seo` (12.1).
- REST для данных, одно WebSocket-подключение на вкладку для лобби, подбора и партий (ТЗ §6). Формы — F4; типы и схемы — `packages/protocol`.
- MUST: главная ≤ 300 КБ gzip без движка (ТЗ §5): Stockfish WASM, разбор и графики — ленивая загрузка.
- MUST: Stockfish WASM — со своего домена, без сторонних CDN и трекеров (ТЗ §5).
- Папки (по умолчанию): `apps/web/src/pages/`; `src/features/<модуль>/` по модулям бэкенда (`games`, `challenges`, `matchmaking`, `rating`, `users`, `profile`, `auth`, `feedback`); `src/shared/` — `api` (клиент REST и WebSocket поверх `packages/protocol`), `i18n`, `ui`. Компоненты и токены — F5.
- MUST NOT: объявлять в `apps/web` свои типы сообщений сервера — только из `packages/protocol`.
- Строки переводов RU/EN — в `packages/i18n`: их читают и `apps/web`, и шаблоны `seo` (ТЗ §5 «Локализация»).

### 12.1. Публичные страницы для поисковиков (F2-Q4)

Решение человека: SEO нужен для профиля, таблицы лидеров и завершённой партии. Способ — A5, ADR-0003.

| Маршрут (форма — F4) | Мета-теги | Серверная разметка |
|---|---|---|
| профиль игрока | `title` «ник — рейтинги», `description`, Open Graph (аватар), `canonical` | ник, рейтинги по категориям, статистика, ссылки на последние партии |
| таблица лидеров по категории | `title`, `description`, `canonical` | топ-100: место, ник со ссылкой, рейтинг, число партий (тот же кэш 5 мин, A13) |
| завершённая партия | `title` «белые — чёрные, результат», `description`, `canonical` | игроки, контроль, результат, окончание, PGN в `<pre>` |

- Как работает: на запрос публичного маршрута `seo` берёт данные через `service` других модулей (таблица 7.1), подставляет мета-теги в `<head>` собранного `index.html` и семантическую разметку в корневой элемент. React монтируется через `createRoot` (не гидрация) и заменяет разметку своим интерфейсом. Остальные маршруты получают обычный `index.html`.
- Язык разметки — из `Accept-Language`, как язык по умолчанию на клиенте (ТЗ §5); строки — из `packages/i18n`.
- `sitemap.xml` — генерируется по запросу из БД: лидеры, профили игроков с партиями, завершённые партии; кэш 1 ч. `robots.txt` — статический.
- MUST: экранировать все данные пользователя в шаблонах (ник, PGN); как именно — F3.
- MUST NOT: индексировать текущие партии, страницы удалённого игрока и закрытые разделы — им `noindex` и они не попадают в `sitemap.xml`.
- MUST NOT: тянуть React, `apps/web` или стили интерфейса в шаблоны `seo` — разметка простая, вид страницы даёт SPA.
- Пример: поисковик запрашивает профиль `knight_rider-7` → `title` «knight_rider-7 — блиц 1642, рапид 1580?», в теле — таблица рейтингов и ссылки на 10 последних партий; браузер игрока через доли секунды видит обычный профиль SPA.

## 15. План роста

Каждый шаг — только по измеренному признаку (метрики A22), не заранее.

| Признак | Шаг |
|---|---|
| p95 доставки хода > 100 мс или p99 задержки event loop > 50 мс в пике 3 дня подряд | Профилировать и убрать синхронную работу; затем VPS с более быстрым CPU |
| После этого CPU процесса `app` > 70% одного ядра в пике; или выкатки дают > 1% прерванных партий за месяц (7.5) | Второй `app` и Redis: pub/sub, Seek, онлайн-статусы; партия закреплена за процессом по `game_id` |
| p95 REST > 50 мс в пике из-за проверки Session | Кэш Session в памяти с инвалидацией при выходе |
| `db` > 50% памяти VPS | PostgreSQL на отдельный VPS или в управляемую БД |
| Скриншоты > 10 ГБ | Объектное хранилище |
| Поисковая консоль показывает, что страницы с серверной разметкой индексируются хуже ожидаемого, или нужны интерактивные публичные страницы без JS | React SSR с гидрацией в том же `app` (без отдельного процесса) |
| Тестировщикам нужен staging с долгоживущими данными | Постоянный staging с бэкапом |
