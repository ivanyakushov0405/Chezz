## 1. Правила для агентов

- MUST: `user_id` текущего игрока берётся только из Session (раздел 5). `user_id`, `white_id`, `creator_id` и цвет из тела запроса или сообщения WebSocket не принимаются как «кто я».
- MUST: каждое входящее тело REST и сообщение WebSocket проверяется строгой схемой zod из `packages/protocol` (ARCHITECTURE A14); лишние поля — ошибка.
- MUST: ход, часы и итог партии решает сервер (ТЗ §4.6, §5; раздел 8). Время с клиента не принимается ни в каком виде.
- MUST: изменяющие запросы — только POST/PUT/PATCH/DELETE с проверкой `Origin` (раздел 6). GET ничего не меняет.
- MUST: данные пользователя в HTML — только через экранирование (раздел 10). MUST NOT: `dangerouslySetInnerHTML`, `innerHTML`, `v-html`-подобное с данными пользователя.
- MUST NOT: отдавать наружу `email`, `google_sub`, `google_name`, `settings`, `terms_accepted_at` чужого User (раздел 12).
- MUST NOT: писать в логи, Sentry и `analytics_events` cookie, токены, `code`/`state` OAuth, e-mail, имя из Google, текст Feedback (раздел 15).
- MUST NOT: секреты в репозитории, образе, клиентском бандле, логах (раздел 17). MUST NOT: тестовые входы в обход Google в коде `app` (раздел 4).
- MUST NOT: агентам — SSH-ключи, пароли БД prod/staging, запуск `scripts/ops/` (раздел 16), GitHub-токен с правом `workflow` или правами администратора репозитория (раздел 17).
- MUST NOT: вводить роли, права и эндпоинты администратора: админ-панель вне этапа (BUSINESS §1.7, D5).

## 4. Вход через Google

Поток (S1), маршруты — F4:
1. `GET` начала входа: `app` создаёт `state`, `nonce`, `code_verifier` (PKCE S256), проверяет `returnTo` (ниже), кладёт всё это в подписанную cookie `__Host-oidc` (`HttpOnly`, `Secure`, `SameSite=Lax`, 10 мин) и перенаправляет на Google. `scope = openid email profile`.
2. Возврат от Google: `state` из запроса = `state` из cookie, иначе отказ (T4, login CSRF). Cookie `__Host-oidc` удаляется в любом исходе.
3. `app` меняет `code` на токены у Google с `client_secret` и `code_verifier` (`openid-client`).
4. Проверка ID-токена (ТЗ §5) — MUST все пункты: подпись по ключам Google (JWKS, кэш `openid-client`); `iss` ∈ {`https://accounts.google.com`, `accounts.google.com`}; `aud` = `GOOGLE_CLIENT_ID` этой среды; `exp` не истёк, `iat` не из будущего (допуск 60 с); `nonce` = `nonce` из cookie.
5. Ищем User по `sub`. Нет — создаём: `google_sub`, `email` (только при `email_verified`, S19), `google_name` (`name`), `avatar_url` (`picture`, раздел 10), `locale` — из браузера (ТЗ §5). Есть — обновляем `email`, `google_name`, `avatar_url` из токена.
6. Создаём Session (раздел 5), ставим cookie, редирект на `returnTo` из `__Host-oidc`.

- MUST (S30): `returnTo` берётся только из `__Host-oidc`, не из запроса возврата от Google. Проверка — одна функция `safeLocalPath` в `platform`: (1) отказ, если в строке есть символ с кодом < 0x20, 0x7F или `\`, или она не начинается с `/`; (2) `u = new URL(returnTo, ORIGIN)`; отказ, если `u.origin !== ORIGIN` или `u.pathname` начинается с `//`; (3) редирект — на абсолютный `u.href` (всегда свой origin). При отказе — `ORIGIN + "/"`. Пример: `/challenge/3f9c…` — разрешён; `//evil.example`, `/%09/evil.example`, `/\evil.example`, `/.//evil.example`, `https://evil.example` — заменяются на `/`. MUST: все эти строки — в unit-тесте функции.
- GET начала входа всегда ведёт к входу; цель «удаление» в нём не принимается (раздел 4.1).
- MUST NOT: принимать ID-токен или `sub` от клиента; хранить access/refresh-токены Google — они не нужны.
- MUST NOT: тестовый вход, «магический» пользователь, обход проверки по переменной окружения. Локально и в CI — свой клиент Google (S25) или сид Session (S26).
- Ошибка входа — страница «Не удалось войти» без подробностей; причина — в лог (без `code`, `state`, токенов, раздел 15).

### 4.1. Подтверждение удаления аккаунта (S31)

Цель: удалить может только владелец, который сейчас за своим браузером и в своём Google; чужая ссылка или украденная cookie не удаляют.

1. `POST` начала удаления — проверка `Origin` (раздел 6) и Session игрока. `app` создаёт `state`, `nonce`, `code_verifier` и кладёт в `__Host-oidc` цель `delete`, `id` текущей Session и `started_at`. Ответ — URL Google с `prompt=select_account` (на стороне Google всегда нужен явный выбор аккаунта) и `max_age=300`; клиент переходит по нему.
2. Возврат от Google — шаги 2–4 раздела 4 и дополнительно: в `__Host-sid` та же Session, что в `__Host-oidc`; `sub` = `google_sub` её User; с `started_at` прошло ≤ 5 мин по часам `app`; если в токене есть `auth_time` — он не старше 5 мин (если нет — свежесть даёт `started_at`). Ничего не удаляется и Session не создаётся.
3. При успехе `app` ставит cookie `__Host-del` (подписанная, `HttpOnly`, `Secure`, `SameSite=Strict`, `Max-Age=300`; внутри — `id` Session и срок) и редиректит на страницу подтверждения «Удалить аккаунт навсегда?».
4. Кнопка подтверждения — `POST` удаления: проверка `Origin`, Session, `__Host-del` с тем же `id` Session и не истёкшим сроком. Выполняется раздел 13, `__Host-del` стирается.

- MUST NOT: удалять аккаунт в обработчике GET, в том числе на возврате от Google.
- Пример: на чужом сайте `<img src="https://<домен>/auth/google/start?purpose=delete">` → обычный вход (цель игнорируется), аккаунт не меняется. Злоумышленник с украденной cookie доходит до шага 1, но на шаге 2 нужен вход в Google жертвы.

## 5. Session и cookie

Таблица `sessions` (владелец — модуль `auth`, ARCHITECTURE §8), по умолчанию:

| Поле | Что |
|---|---|
| `id` | UUID, внутренний ключ (для закрытия WebSocket) |
| `token_hash` | SHA-256 токена из cookie, уникальный индекс |
| `user_id` | User |
| `created_at`, `expires_at` | `expires_at = created_at + 30 дней` (ТЗ §4.1 п.5) |

- Токен — `crypto.randomBytes(32)` в base64url, только в cookie `__Host-sid` (S4), `Max-Age` = 30 дней.
- Проверка — на каждый REST-запрос и при открытии WebSocket: хэш токена → строка с `expires_at > now()` (ARCHITECTURE A20). Нет строки — запрос как от гостя; на защищённых маршрутах — 401.
- Открытый WebSocket закрывается в момент `expires_at` своей Session. Кроме того, `realtime` раз в 60 с одним запросом проверяет, что Session всех открытых соединений ещё есть, и закрывает соединения отсутствующих (S6) — так срабатывает и отзыв скриптом `logout-everyone.sql`.
- «Выйти» — удалить текущую строку и cookie. «Выйти со всех устройств» — удалить все строки `user_id` (ТЗ §4.1 п.5). В обоих случаях `auth` сообщает `realtime`, какие Session закрыты, и тот закрывает их WebSocket (S6; событие `auth` — F3-Q3).
- Истёкшие строки удаляются при старте `app` и раз в сутки.
- Первый вход (S5): пока у User пуст `nickname` или `terms_accepted_at`, разрешены только: прочитать своё состояние, выбрать ник и принять правила (одним запросом), выйти, удалить аккаунт (раздел 4.1), отправить Feedback (как гость, ТЗ §4.12). Остальное — 403 с кодом «нужен первый вход» (форма — F4). WebSocket такой Session работает как у гостя.
- MUST NOT: токен в URL, `localStorage`, теле ответа, логах.
- Пример: игрок вошёл с телефона и ноутбука → две строки `sessions`. На ноутбуке «Выйти со всех устройств» → обе удалены, WebSocket на телефоне закрыт, идущая партия продолжается по правилам переподключения (ТЗ §4.6), пока игрок не войдёт снова.

## 6. CSRF и заголовки

CSRF (S7, T5):
- MUST: POST/PUT/PATCH/DELETE — `Origin` равен origin среды (`https://<домен>`); нет `Origin` или другой — 403. Тела — `application/json`; исключение — `multipart/form-data` загрузки Feedback, тоже с проверкой `Origin`.
- MUST: WebSocket-upgrade — та же проверка `Origin` до проверки Session.
- Вход защищён `state` (раздел 4).

Заголовки на всех ответах — ставит `edge` (S8); Caddyfile — F7, содержание — здесь:

| Заголовок | Значение |
|---|---|
| `Strict-Transport-Security` | `max-age=31536000` (без `preload`) |
| `Content-Security-Policy` | `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; worker-src 'self' blob:; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https://lh3.googleusercontent.com; connect-src 'self' wss://<домен> https://<ingest Sentry>; font-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` |

- `'wasm-unsafe-eval'` — для Stockfish WASM (ТЗ §4.9); `'unsafe-inline'` в стилях — chessground ставит координаты фигур атрибутом `style`. Скрипты inline запрещены: SPA и `seo` не вставляют `<script>` с кодом в HTML.
- HTTP → HTTPS — редирект Caddy; WebSocket — только `wss://` (ТЗ §5).
- MUST NOT: новый домен в CSP без правки этого раздела и ARCHITECTURE §14.

- MUST NOT: у аккаунта Ivan особых прав в `app` — он такой же Игрок.

## 8. Целостность партии

- Ход: сервер берёт сторону из Session (раздел 7), проверяет очередь хода, номер полухода (S10) и допустимость через `packages/chess` (ARCHITECTURE §10). Неверный номер — отказ без изменения; клиент получает снимок (ARCHITECTURE §9.1 п.5).
- Часы — только серверные, монотонное время (ARCHITECTURE §9.2). Клиент не присылает ни остаток, ни время хода.
- Компенсация задержки — по RTT, который измеряет сервер своими ping/pong (ARCHITECTURE A11), не по данным клиента; потолок 1 с на ход (ТЗ §4.6). Остаточный риск: клиент может задерживать pong и получать до 1 с на ход — допускает само ТЗ.
- Команды одной партии выполняются строго по очереди `GameRoom` (ARCHITECTURE A9): «ход» и «флаг» не применяются одновременно.
- Предложения ничьей и возврата хода: `GameRoom` хранит `offer.by` (сторону); ответ принимается только от другой стороны (S29). Ход предложившего снимает его предложение ничьей; любой ход снимает предложение возврата.
- Итог и рейтинг меняет только сервер при конце партии (ARCHITECTURE §9.1 п.7). Эндпоинта «записать результат» нет.
- Пример: в пуле 1+0 у белых осталось 0,2 с; клиент белых отправил ход, когда серверные часы уже ≤ 0 → сервер фиксирует флаг (`timeout`), ход отклонён, клиент показывает позицию сервера.

## 9. Лимиты и размеры

Значения по умолчанию, основаны на допущении BUSINESS D2 (≤ 100 сообщений WebSocket/с и ≤ 20 REST/с на весь сервис). Счётчики — в памяти `app` (S11, ARCHITECTURE A8, A21). Кто регистрирует лимит по User — ARCHITECTURE F2-Q9.

Базовый набор (S11, ревью r1 prop-5):

| Что | Лимит | Ключ |
|---|---|---|
| REST API, включая вход, вызовы и WebSocket-upgrade (без статики и HTML страниц) | 300/мин гость, 300/мин игрок | IP / User |
| Feedback | 5/ч игрок, 3/ч гость | User / IP |
| Открытых WebSocket | 5 на User; без Session — 50 на IP | User / IP |
| Сообщения WebSocket | token bucket 10/с, запас 20 | соединение |
| Размеры | ниже | — |

- Лимиты по IP выбраны с запасом под мобильный CGNAT и школьный NAT: 300/мин — это 5 запросов/с с одного адреса.
- WebSocket-upgrade считается в общий лимит REST (ARCHITECTURE A21: `@fastify/rate-limit` на upgrade): цикл «открыл–закрыл» упирается в 300/мин.
- Сообщения на User ограничены произведением: ≤ 5 соединений × 10/с. Отдельный token bucket на User (A21) не вводится — правка A21 в F3-Q3.
- Лимит на соединение — потолок для одного клиента, а не ожидаемый трафик: реальный пик — ≤ 100 сообщений/с на сервис (BUSINESS D2).
- Отдельные лимиты на начало входа, upgrade, создание вызовов и сообщения по User — по признаку: в логах флуд, который базовый набор не держит.

- Превышение REST — 429. Превышение WebSocket — сообщение отбрасывается с ошибкой «слишком часто»; корзина пуста дольше 10 с — соединение закрывается кодом 1008.
- Размеры: сообщение WebSocket ≤ 4 КБ (`maxPayload`); тело REST ≤ 16 КБ; загрузка Feedback ≤ 5 МБ (раздел 11).
- IP клиента — из `X-Forwarded-For`, только от `edge`: Fastify `trustProxy` — адрес `edge` в сети Docker, не `true`.
- Нагрузочный тест (ТЗ §7): 150 игроков с разных Session укладываются в лимиты по User; лимит по IP на staging поднимается переменной окружения среды, на prod — нет.
- Пример: бот шлёт 50 «предложить ничью» в секунду → после 20 сообщений отказы, через 10 с соединение закрыто; партии соперника это не мешает. Открыть 6-ю вкладку тем же игроком — 6-е соединение отклонено.

## 10. Вывод данных пользователя (XSS)

Данные из внешнего мира: ник (уже ограничен `[A-Za-z0-9_-]`, ТЗ §4.1 п.3), `google_name`, `avatar_url`, `country`, текст и `meta` Feedback, PGN при выдаче (S13).

- SPA: React экранирует текст сам. MUST NOT: `dangerouslySetInnerHTML` с любыми данными пользователя.
- `seo` (S12): все подстановки — через функцию-шаблон `html` в `apps/server/src/seo/html.ts`, которая экранирует `& < > " '` по умолчанию; вставка готового фрагмента — только явным `raw()` для результата другого `html`. MUST NOT: склеивать HTML строками.
- Атрибуты `href` и `src` в `seo` и SPA собираются только из `id` и `encodeURIComponent(nickname)`, не из сырых строк пользователя.
- `avatar_url`: показывается, только если начинается с `https://lh3.googleusercontent.com/`; иначе — аватар по умолчанию. Аватар грузится с домена Google (ТЗ §4.2 «аватар из Google»), это единственный сторонний домен картинок (CSP, раздел 6).
- `country` — только код из списка стран (ISO 3166-1 alpha-2), не свободный текст.
- PGN в `<pre>` (ARCHITECTURE §12.1) — экранирован как текст.
- Данные в `<script>` — не вставляются (раздел 6, inline-скрипты запрещены). Если понадобится — JSON, в котором каждый символ `<` заменён на шестисимвольную escape-последовательность JSON «обратная косая черта, u, 0, 0, 3, c», через правку этого раздела.
- Пример: `google_name` = `<img src=x onerror=alert(1)>` — в интерфейсе не показывается (GLOSSARY G17), а в логах и скриптах `scripts/ops/` выводится как текст.

## 11. Feedback и скриншоты

- Пример: гость на странице партии отправил текст и `bug.png` 1,2 МБ → `Feedback{user_id: пусто, screenshot_url: "7b1e….png", meta: {url: "/game/9a…", browser: "Mozilla/5.0 …", game_id: "9a…"}}`. Файл `report.svg` → отказ «неподдерживаемый формат».

## 13. Удаление аккаунта

Закрывает GLOSSARY Q6. Запускается подтверждающим `POST` раздела 4.1. Сценарий — `auth.service`. Ему нужны зависимости `auth` → `games`, `challenges`, `matchmaking`, которых нет в ARCHITECTURE §7.1; правка — в F3-Q3 (цикла нет: ни один из трёх не зависит от `auth`).

0. До транзакции: `matchmaking.service` снимает Seek игрока (память).
1. Транзакция: `users.service.lockForGame(trx, [user_id])` — та же блокировка строки User, что при создании партии (ARCHITECTURE §9.1), поэтому новая партия не появится между проверкой и удалением. `games.service` — есть `active` Game → отказ «сначала закончите партию» (S17).
2. Открытый Challenge игрока → `cancelled` (через `challenges.service`, в той же `trx`).
3. `users.service.anonymize(trx, user_id)`: `google_sub`, `email`, `google_name`, `avatar_url`, `country`, `nickname`, `terms_accepted_at` → NULL; `settings` → по умолчанию; `deleted_at` → сейчас (S16). Ник освобождается и может быть занят другим (резервирование отклонено в ревью r1, sec-10: хранить старый ник — хранить ПДн удалённого; риск подмены в тестовой бете мал).
4. `feedback.service.anonymize(trx, user_id)`: `user_id` → NULL, `screenshot_url` → NULL; текст и `meta` остаются (S15).
5. Все Session игрока удаляются (S6).
6. После коммита: файлы скриншотов удаляются с тома; WebSocket закрываются; cookie стирается.

Не меняется: `games`, `ratings`, `rating_history`, `analytics_events` — они ссылаются на `user_id`, за которым больше нет ПДн.

Показ после удаления:
- Ник в партиях, PGN (S13), истории соперников — «удалённый игрок» / «Deleted player» (GLOSSARY §5).
- Профиль — заглушка «удалённый игрок» с `noindex` (ARCHITECTURE §12.1); нет в таблице лидеров, `sitemap.xml`, лобби.
- Повторный вход тем же Google — новый аккаунт с рейтингом 1500 (`google_sub` очищен).

- MUST: `games.service.createGame` отказывает, если у кого-то из игроков `deleted_at` не пуст (флаг возвращает `lockForGame`) — так закрыта гонка с Seek, который подбор успел свести до шага 0. Правка ARCHITECTURE §9.1 — F3-Q3.
- MUST (S31): удаление — только по шагам раздела 4.1; форма — F4, F5.
- MUST: удаление — только из профиля самим игроком. Скрипта удаления на проде нет; на письма «удалите мой аккаунт» ответ — «войдите и удалите в профиле» (случай без доступа к Google — F3-Q5).
- MUST: если шаг 6 упал (файл не удалился), это ошибка в Sentry; ежедневная чистка удаляет файлы, на которые не ссылается ни одна строка `feedback` (раздел 14).
- Пример: `knight_rider-7` удалил аккаунт → в его партии с `queen_b` PGN выдаётся с `[White "Deleted player"]`, рейтинг `queen_b` и её история не меняются.

## 14. Сроки хранения

| Данные | Срок | Как удаляется |
|---|---|---|
| Session | 30 дней (ТЗ §4.1 п.5) | автоматически: при старте `app` и раз в сутки (раздел 5) |
| Скриншоты Feedback | 90 дней | автоматически раз в сутки модулем `feedback` (S20): у строк старше 90 дней `screenshot_url` → NULL, затем удаляются файлы тома старше 1 ч, на которые не ссылается ни одна строка `feedback` (порог 1 ч — чтобы не задеть файл, чья строка ещё не записана; так же убираются файлы, оставшиеся после сбоя удаления аккаунта) |
| Текст Feedback | до конца беты | вручную после решения F3-Q2 |
| User, партии, рейтинги | пока аккаунт не удалён; после беты — F3-Q2 (ТЗ §8) | удаление аккаунта (раздел 13) |
| `analytics_events` | до конца беты | вручную после решения F3-Q2 |
| Логи `app` и `edge` | 14 дней | ротация логов Docker (настройка — F7) |
| События Sentry | срок тарифа Sentry (по умолчанию бесплатного — 30 дней) | Sentry |
| Бэкап БД | 14 дней (ТЗ §5), зашифрован (S21) | задача бэкапа (F7) |

- Ежедневные чистки — таймеры в процессе `app` (ARCHITECTURE A1): каждый модуль чистит свои таблицы и файлы своим `service`. Отдельного процесса нет.
- Проверка восстановления раз в месяц (ТЗ §5, S35): на prod-VPS запускается временный контейнер PostgreSQL без публикации портов; последний бэкап расшифровывается ключом `age`, который Ivan передаёт через stdin (`age -d -i -`), ключ на диск не пишется; восстановленная БД проверяется запросом числа строк основных таблиц; контейнер и его том удаляются. Скрипт и место записи результата — F7.
- Требование к F7: хранилище копий — без права удаления у ключа с VPS (неизменяемые объекты или отдельный ключ только на запись), чтобы захват VPS не стирал копии.

## 15. Логи, Sentry, аналитика

Логи (`pino`, ARCHITECTURE A22):
- MUST: сериализатор запроса пишет метод, путь **без строки запроса**, статус, время, `request_id`, `user_id` (если есть), IP. Строка запроса не пишется: в ней `code` и `state` OAuth.
- MUST NOT: заголовки `Cookie`, `Set-Cookie`, `Authorization`; тела запросов; токены; e-mail; `google_name`; текст Feedback. Настройка — `redact` в `pino` для путей `req.headers.cookie`, `req.headers.authorization`, `res.headers["set-cookie"]`.
- Пример строки: `{"level":"info","req":{"method":"POST","path":"/api/challenges"},"status":201,"user_id":"…","ms":7}`.

Sentry (клиент и сервер):
- MUST: `sendDefaultPii: false`; в `beforeSend` удалять cookie, заголовки, тело запроса, строку запроса; пользователь — только `id`.
- MUST NOT: Session Replay и запись экрана.

Аналитика (ARCHITECTURE §7.5):
- MUST: `analytics_events.props` — только технические значения (`wait_ms`, `termination`, `after_restart`); `user_id` и `game_id` — в своих колонках. MUST NOT: e-mail, имя, ник, IP, User-Agent в `props`.

## 16. Доступ человека к проду

Закрывает GLOSSARY Q10. Сотрудник один — Ivan (BUSINESS D4); админ-панели нет (D5).

VPS:

БД:
- Одна роль `app` (миграции и данные). Отдельной роли для чтения нет (ревью r1, prop-3): кто вошёл на VPS по SSH и может `docker exec`, тот и так root на машине; защита от случайной правки — транзакция только для чтения. Суперпользователь `postgres` — только для обслуживания самой БД.
- Чтение: `ssh` → обёртка `scripts/ops/ro.sh`, которая запускает `docker compose exec -e PGOPTIONS='-c default_transaction_read_only=on' db psql -U app` (`~/.psqlrc` VPS внутри контейнера не действует). Пример: последние отзывы — `scripts/ops/feedback-recent.sql` (дата, текст, `meta`, ключ скриншота, ник автора).
- Скриншоты: `scp` с тома на свою машину; после разбора — удалить локальную копию.
- Изменения — только скриптом из `scripts/ops/` в git, запуск `psql -U app -v ON_ERROR_STOP=1 --single-transaction -f …`. Отдельного журнала и ревью нет: сопровождающий один (D4), история скрипта — в git (ревью r1, prop-1). Скрипт пока один: `logout-everyone.sql` (раздел 17); открытые WebSocket закрываются перепроверкой Session за ≤ 60 с (раздел 5).
- Модерации нет (BUSINESS D5): скриптов смены ника, бана и т. п. не пишем (ревью r1, tz-2). Удаление аккаунта — только из профиля (раздел 13).
- MUST NOT: произвольный `UPDATE`/`DELETE` на проде из консоли; копия БД prod на свою машину или в staging (S26). Исключение — проверка восстановления по разделу 14 (S35).
- Агенты: MUST NOT иметь SSH-ключи, пароли БД, `.env` сред; писать скрипты `scripts/ops/` могут, запускает только Ivan.

Защита GitHub (S24; включение — F7, F8):

- MUST: ветка `main` защищена: изменения только через PR, мерж — Ivan; `.github/workflows/**` и `deploy/**` — в CODEOWNERS за Ivan.

- Клиент Google staging — в режиме «Testing» со списком тестовых пользователей (S33): посторонние не войдут на staging и не оставят там ПДн.

Session от смены секретов не зависят; при подозрении на кражу токенов — `DELETE FROM sessions` скриптом `scripts/ops/logout-everyone.sql`.
