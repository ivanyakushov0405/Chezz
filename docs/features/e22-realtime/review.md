### Блокеры
- [apps/server/src/realtime/api.ts:16-19] `preClose` ждёт `websocketServer.close(cb)`. У `ws` 8 с `noServer` и `clientTracking` колбэк срабатывает, только когда закрылись **все** клиенты. Клиент, который не ответил на кадр закрытия 1012 (полуоткрытый TCP мобильного клиента — обычное дело), держит остановку до `closeTimeout` `ws` (30 с по умолчанию). Пока висит `preClose`, не идут `onClose`: `realtime.stop`, `auth.stop`, `analytics.drain`, `metrics.stop` и `db.destroy` в `main.ts`. Docker по умолчанию убивает процесс через 10 с (SIGKILL), и начатые записи аналитики теряются. Это ломает ожидание API §10 («через 0,5–2 с клиент подключён») и простой выкатки (OPERATIONS O13, ARCHITECTURE A10). Тест К-10 этого не ловит: тестовый клиент отвечает на close сразу. → После `svc.closeAll()` вызывать `terminate()` у соединений, которые не закрылись за короткий срок (например, 1–2 с через `TimeSource.setTimer`, A27), или вызывать `done()`, не дожидаясь `close` сервера `ws`. Добавить тест: клиент не отвечает на close (`socket.pause()` или сырой TCP) → `shutdown()` завершается в срок. (Чек-лист п.2 «корректность / утечки ресурсов»; API §10; OPERATIONS O13.)

### Желательно
- [apps/server/src/realtime/service.ts:214-226, 349-352] Токен корзины берётся при **обработке** из очереди (`time.now()` в `dispatch`), а не при приходе сообщения. Сейчас обработчик есть только у `pong`, и это безвредно. С E06 медленный обработчик (транзакция хода) накопит неограниченную очередь замыканий, а время корзины сдвинется к моменту обработки. Лучше брать токен в обработчике `"message"` и ставить в очередь только принятые сообщения. Тогда отказ `rate_limited` и закрытие 1008 тоже сработают сразу (SECURITY §9, A21).
- [apps/server/src/realtime/domain/bucket.ts:49-53, 67] У «пуста дольше 10 с» своя трактовка: отсчёт идёт от первого отказа и сбрасывается только приёмом при ≥ 2 токенах. С примером SECURITY §9 она сходится (бот 50/с закрыт через 10 с; есть тест К-7). Но клиента, который после одного отказа держит ровно ~10/с, закроют, хотя каждое его сообщение принимается. Решение записано только в `log.md` — перенести его в раздел «Решения» `brief.md`, ведь это толкование правила SECURITY §9.
- [apps/server/src/realtime/api.ts:13-20] Нет своего `errorHandler` `@fastify/websocket`. Стандартный пишет `request.log.error(error)` на каждый обрыв клиента (ECONNRESET) и каждое превышение `maxPayload` (1009). На бете это шум уровня error и ложные срабатывания алертов. Лучше передать `errorHandler`: обрыв и `maxPayload` писать на уровне `warn`/`info` и закрывать соединение через `terminate`; счётчики снимет `release` по `close`.
- [apps/server/src/platform/http.ts:54-58, 118-124] Origin проверяется только для upgrade на `/ws`. Upgrade на другие GET-маршруты, зарегистрированные после плагина (`users`, `auth`), проходит рукопожатие 101 с чужим Origin: обработчик `noHandle` `@fastify/websocket` сразу закрывает соединение. При этом Session читается. Данные не утекают, но буква SECURITY §6 («WebSocket-upgrade — та же проверка Origin до Session») для этих путей не соблюдена. Лучше проверять Origin у любого `upgrade: websocket` или отвечать 404 на upgrade вне `/ws`.
- [apps/server/src/realtime/service.ts:174] Таймер на `expires_at` ставится, только если срок наступит не позже чем через `SESSION_RECHECK_MS`. Следующая перепроверка начинается через 60 с **после окончания** предыдущей (`every`). Если до срока чуть больше 60 с, соединение закроется на следующей перепроверке, то есть позже `expires_at` на время запроса. Расхождение в миллисекундах, но порог `2 × SESSION_RECHECK_MS` закрыл бы его полностью (SECURITY §5, «в момент `expires_at`»).
- [apps/server/src/realtime/service.ts:243-268] Путь «отказ по правам → `error` без вызова обработчика» и обработка ошибок обработчика (`AppError` → его код, иное → `internal` и Sentry) не покрыты тестом сервиса. Отказ проверен только чистой функцией `rights.test.ts`, а сквозной путь сейчас недостижим: в `ClientMessage` только `pong`. Нет и теста, что `ctx.rtt_ms` обновляется по `pong`. Стоит добавить unit-тест в `service.test.ts` с `FakeSocket` и обработчиком-шпионом, когда в протоколе появится первая команда (E06), или уже сейчас — через подмену схемы. (К-6, К-8.)
- [apps/server/src/realtime/messages.int.test.ts:58; apps/server/src/realtime/domain/bucket.test.ts:63] Метка `E-1` в имени теста не относится ни к одному критерию брифа (TESTING §1: только номера `К-n`). Убрать или заменить на `К-5` / `К-7`.
- [apps/server/src/realtime/session.int.test.ts:79-86] «Закрытие в момент `expires_at`» опирается на реальные паузы (`setTimeout` 100 / 50 мс): за это время должен успеть пройти запрос перепроверки к БД. На загруженном CI тест может стать нестабильным. Надёжнее ждать условие (`eventually`) или признак завершения перепроверки.
- [docs/features/e22-realtime/brief.md:29] В шаге 3 бриф называет `rtt.ts`, а файл — `domain/ping.ts`. Мелочь, но бриф стоит поправить.
