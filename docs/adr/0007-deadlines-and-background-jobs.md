# ADR-0007. Сроки и фоновые задачи в одном процессе: переживают перезапуск

Статус: предложено. Дата: 2026-11-05 (architect, режим roadmap; ROADMAP «Сквозные решения» п.3).

## Контекст
Кроме таймеров `GameRoom` (ARCHITECTURE §9.1 п.6, §9.3) в `app` есть: истечение вызова через 30 мин (ТЗ §4.3 п.4), чистка истёкших Session при старте и раз в сутки (SECURITY §5), чистка скриншотов раз в сутки (SECURITY §14), кэш таблицы лидеров 5 мин (A13), проход подбора раз в 1 с (ТЗ §4.4), перепроверка Session открытых WebSocket раз в 60 с (§9.1 п.9), ping раз в 5 с (A11). Всё — в одном процессе (A1), время — только через `TimeSource` (A27), очередей и хранилищ сверх PostgreSQL нет (ADR-0002). `app` перезапускается при каждой выкатке, поэтому таймер в памяти может не сработать никогда.

## Решение
1. **Срок — колонка в БД, таймер — только ускоритель.** Каждый срок, который должен пережить перезапуск, хранится как время по стене (`expires_at`, `wallNow`). Правильность не зависит от срабатывания таймера: любая операция, зависящая от срока, сама проверяет его в своём запросе (`expires_at > now`, где `now = time.wallNow()`). Пример: принятие вызова, у которого `status = open`, но `expires_at` прошёл, — `challenge_expired` (ADR-0008 п.3), даже если таймер ещё не сработал; лобби не показывает такие вызовы.
2. **Таймер переводит состояние и публикует событие.** При создании записи — `time.setTimer(expires_at − wallNow, fn)`; `fn` — условный `UPDATE … SET status = 'expired' WHERE id = $1 AND status = 'open' AND expires_at <= $now`; изменилась строка — событие (`challenge_closed`). Повторный или опоздавший запуск ничего не ломает.
3. **Восстановление при старте** — в `start()` сервиса (ADR-0005 п.9): (а) одним запросом переводит все просроченные записи и публикует события; (б) ставит таймеры на будущие сроки. Для вызовов это ≤ 1 открытый на User, то есть тысячи таймеров максимум.
4. **Периодические задачи** — `platform/schedule.ts`: `every(time, {name, interval_ms, run_at_start}, fn)` поверх `time.setTimer`. Следующий запуск ставится после окончания предыдущего (без наложения); ошибка → лог и Sentry, расписание продолжается. Суточные чистки (Session — `auth`, скриншоты — `feedback`) — `interval_ms` = 24 ч и `run_at_start: true`: пропущенный из-за перезапуска запуск закрывается запуском при старте. Время суток не задаётся, таблицы задач нет. Задачи идемпотентны, асинхронны (`fs/promises`, без синхронного `fs`, ARCHITECTURE §1).
5. **Только в памяти** — проход подбора (1 с), перепроверка Session (60 с), ping (5 с) — тот же `every`; восстанавливать нечего (Seek теряются при перезапуске, ADR-0002).
6. **Кэши без таймера.** Таблица лидеров (5 мин) — срок жизни проверяется при чтении по `time.now()`; одновременно идёт не больше одного запроса пересчёта, остальные ждут его результат.
7. **`GameRoom`** — по ARCHITECTURE §9.3 без изменений; этот ADR его не трогает.
8. **Тесты.** `ManualTimeSource.advance` срабатывает таймеры и `every` (TESTING §7.2). Восстановление: фабрика вставляет запись со сроком в прошлом → `startApp()` → запись переведена, событие отправлено, операция по ней отклонена. Опоздавший таймер: `advance` меньше срока + операция с `wallNow` после срока → отказ по п.1.
9. `TimeSource.setTimer` обязан поддерживать задержки до 24 ч включительно; более длинные сроки одним таймером не ставятся (только через `every` или п.3).

## Последствия
- Перезапуск `app` не теряет и не продлевает сроки; нового процесса, очереди и таблицы задач нет.
- Модули со сроками пишут `start()` с восстановлением и тест на него — это пункт DoD задач `challenges` (E08), `auth` (E04, чистка Session), `feedback` (E18).
- Правки при apply/reopen: ARCHITECTURE §7.2 (правило п.1–4 одной строкой и ссылка на ADR), §3 (строка), §16; SECURITY §14 — ссылка на `every` вместо «таймеры в процессе `app`».
