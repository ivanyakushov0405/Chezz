# ADR-0008. Порядок блокировок строк: сначала User, потом партия, потом вызов

Статус: предложено. Дата: 2026-11-05 (architect, режим roadmap; ROADMAP «Сквозные решения» п.5).

## Контекст
F2-Q8: гонки «два принятия одного вызова», «принятие против отмены», «принятие против истечения 30 мин». К ним добавляются «принятие против удаления аккаунта создателя» и «создание вызова против удаления» (SECURITY §13, A28). F2-Q8 предлагал блокировать строку вызова **раньше** строк игроков. Но удаление аккаунта (SECURITY §13) уже идёт в обратном порядке: шаг 1 — `lockForGame([user_id])`, шаг 2 — отмена открытого вызова. Принятие «вызов → игроки» против удаления «игрок → вызов» — классическая взаимная блокировка: PostgreSQL убьёт одну транзакцию (`40P01`), пользователь получит 500. Нужен один порядок для всех модулей.

## Решение
1. **Глобальный порядок блокировок в транзакции:** (1) строки `users` — только `users.service.lockForGame(trx, ids)`, все сразу, по возрастанию `id`; (2) `games`; (3) `challenges`; (4) `ratings`, `rating_history` — по возрастанию `user_id`; (5) `feedback`, `sessions`. MUST: транзакция, которой нужны строки `users`, берёт их первым действием; MUST NOT: блокировать `users` после любой другой строки. Транзакции без `users` (отмена вызова, истечение, конец партии) берут строки не более чем двух соседних уровней в этом же порядке.
2. **Создание вызова** (`challenges.service.create`): `lockForGame(trx, [creator_id])` — проверка `deleted_at` и `active` Game (`player_busy`) → вставка (частичный уникальный индекс, `open_challenge_exists`). Закрывает гонку с удалением: вызов удалённого не появится после шага 2 SECURITY §13.
3. **Принятие** (`challenges.service.accept`, ARCHITECTURE §9.1 п.2):
   - до транзакции — чтение вызова без блокировки: `not_found`, `own_challenge`, статус не `open` (`challenge_taken` / `challenge_cancelled` / `challenge_expired`), `expires_at ≤ wallNow` → `challenge_expired`, `rating_out_of_range`;
   - транзакция: `games.service.createGame(trx, …)` (внутри — `lockForGame` по возрастанию `id`, отказ — A28) → условный `UPDATE challenges SET status = 'accepted', game_id = … WHERE id = $1 AND status = 'open' AND expires_at > $now`;
   - обновлено 0 строк → откат (вставка Game откатывается), повторное чтение статуса: `accepted` → `challenge_taken`, `cancelled` → `challenge_cancelled`, иначе → `challenge_expired`.
   - Если в одной гонке вызов уже принят и принимающий занят — отвечает `createGame` (`player_busy`): он выполняется раньше. Приоритет кодов этим и задан.
4. **Отмена создателем и истечение** — один условный `UPDATE … WHERE id = $1 AND status = 'open'` (истечение — ещё `AND expires_at <= $now`, ADR-0007), без блокировки `users`. При READ COMMITTED PostgreSQL перепроверяет `WHERE` по последней версии строки, поэтому из «принять / отменить / истечь» выигрывает ровно один.
5. **Удаление аккаунта** — порядок SECURITY §13 не меняется (`users` → проверка `games` → `challenges` → `users.anonymize` → `feedback` → `sessions`), он уже совпадает с п.1. Отмена вызова на шаге 2 — тем же условным `UPDATE` по `creator_id`, после блокировки User.
6. **Подбор** — только `createGame` (`users` → `games`). **Конец партии** — `games` → `ratings`/`rating_history` (`applyResult`), `users` не блокируются.
7. Уровень изоляции — READ COMMITTED (по умолчанию). Автоповтора нет: `40P01`/`40001` при этом порядке — ошибка в коде, `500` + Sentry.
8. **Проверка** — интеграционные тесты developer `challenges` (E08) двумя соединениями к БД (TESTING §7.1): два принятия → одна Game, второе `challenge_taken`; принятие против отмены; принятие против истечения (`ManualTimeSource`); в E19 — принятие против удаления создателя (A28: `challenge_cancelled`) и создание вызова против удаления. Ни в одном нет `40P01`.

## Последствия
- Один порядок для `challenges`, `matchmaking`, `games`, `auth`; новые сценарии с несколькими блокировками сверяются с п.1 в `design.md`.
- Проигравшее принятие делает лишнюю вставку Game, которая откатывается, — дёшево при ≤ 20 REST/с.
- Правки при apply/reopen: ARCHITECTURE §9.1 п.2–3 (порядок и условный `UPDATE`), §3 (строка), §16, §17 (закрыть F2-Q8 вариантом «сначала User»); API §12.3 — ничего, коды те же.
