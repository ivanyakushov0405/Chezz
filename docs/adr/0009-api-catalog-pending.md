# ADR-0009. Каталог API и код: реализованное и запланированное

Статус: принято (Ivan, 2026-11-06). Предложено: 2026-11-06 (architect, design E01 «Скелет репозитория»; requirements E01, «Открытые вопросы», п.2).

## Контекст
API §16 задаёт две проверки, которые в скелете противоречат друг другу:
- `scripts/check-api-doc.sh` сравнивает каталог документа (коды 5.2, операции 12, `type` 13) с кодом `packages/protocol` в обе стороны;
- `apps/server/src/platform/routes.int.test.ts` требует «маршруты Fastify = `REST_ROUTES`».

Каталог описан целиком на всю бету, а маршруты появляются по эпикам (E01 — только `getHealth`). Если описать в `REST_ROUTES` весь каталог, `routes.int` красный до последнего эпика. Если описать только реализованное, красный `check-api-doc.sh`. Описывать схемы всех операций и сообщений заранее (E01) — тоже плохо: схемы партии и вызовов проектируются в своих эпиках (E06, E08), заранее написанные устареют.

## Решение
1. В `packages/protocol/src/pending.ts` — константа `PENDING_CATALOG = {rest: string[], ws_client: string[], ws_server: string[]}`: операции разделов 12 и `type` разделов 9.1, 9.3, 13, которые есть в документе, но ещё не реализованы. Схем у них в коде нет.
2. `ErrorCode` (`errors.ts`) — всегда полный список раздела 5.2 (обе таблицы), отложенных кодов нет: перечисление дешёвое, а переводы `error.<code>` нужны интерфейсу целиком (DESIGN §11).
3. `npm run -w packages/protocol dump` печатает JSON: `error_codes`, `rest` (операция, метод, путь), `ws_client`, `ws_server`, `pending`.
4. `check-api-doc.sh` проверяет: (а) коды 5.2 = `error_codes`; (б) операции раздела 12 = `rest` ⊔ `pending.rest` — каждая ровно в одном из двух, лишних нет ни там, ни там; у реализованных совпадают метод и путь; (в) то же для `type` 9.1 + 13 (клиент → сервер) и 9.3 + 13 (сервер → клиент). Расхождение называется поимённо в обе стороны.
5. `routes.int.test.ts` не меняется: маршруты `/api/*` = записи `REST_ROUTES` (только реализованные).
6. Эпик, который реализует операцию или сообщение, в той же задаче `[contracts]` переносит имя из `PENDING_CATALOG` в `REST_ROUTES` / `ClientMessage` / `ServerMessage` (API §15). `PENDING_CATALOG` только уменьшается; новая строка каталога без кода сразу попадает в `PENDING_CATALOG`.

## Последствия
- Обе проверки зелёные с первого эпика, ни одна не ослаблена: документ и код сверяются целиком, маршруты и `REST_ROUTES` — точно.
- Схемы появляются вместе с маршрутом, `snapshot/protocol.json` растёт по эпикам; до первого внешнего клиента (этап 5) `PROTOCOL_VERSION` от этого не меняется (новый маршрут и новый `type` — совместимые изменения, API §7).
- Риск — «забытая» операция навсегда в `PENDING_CATALOG`. Мера: сводка фичи (TESTING §14 п.3) перечисляет, что ушло из `PENDING_CATALOG`; к концу этапа 3 (E17) список пуст, кроме операций вне этапов 1–3.
- Правки документов (apply E01): API §2 (P34), §15 (раскладка `pending.ts`, шаг 3), §16 (строка `check-api-doc.sh`); ARCHITECTURE §16 (строка ADR).
