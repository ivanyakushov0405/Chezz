# ADR-0005. Сборка модулей сервера: фабрики, корень сборки, HTTP и WebSocket

Статус: принято (Ivan, 2026-11-05). Предложено: 2026-11-05 (architect, режим roadmap; ROADMAP «Сквозные решения» п.1). Правки документов из «Последствий» внесены в apply E01.

## Контекст
ARCHITECTURE §7.1–7.3 задаёт модули, слои и события, но не то, как модули собираются в процесс `app`. Открыты: F2-Q12 (как `service` получает пул БД, `trx` и чужие сервисы; где тип Kysely `Database`; какой тип называется `Game`), F2-Q10 (что именно модуль может импортировать у другого), API F4-Q6 (`registerRoute` в `platform` проверяет «Кто», а Session знает только `auth`; `realtime` не может импортировать чужие `api.ts`), API F4-Q5 (сигнатуры инструментов скелета). Решение нужно в задаче 2 скелета (E01): там появляются `main.ts`, `app.ts`, `platform/`, `.dependency-cruiser.cjs`. TESTING §7.3: тесты поднимают `app` через `buildApp(config, deps)` со своей БД и `ManualTimeSource`, поэтому в процессе не должно быть глобального состояния модулей.

## Решение
1. **Корень сборки** — `apps/server/src/app.ts`, `buildApp(config, deps)`. Только он (и `main.ts`) импортирует все модули: создаёт сервисы по слоям L0 → L6, регистрирует их `api.ts`, передаёт WS-обработчики в `realtime`. Он не модуль (не лежит в `src/<модуль>/`), правила 7.1 к нему не применяются. `main.ts` читает конфиг, создаёт настоящие `deps` (пул БД, системный `TimeSource`, Sentry), вызывает `buildApp` и `listen`.
2. **Сервис — фабрика.** `src/<m>/service.ts` экспортирует интерфейс `XService` и `createXService(deps: XServiceDeps): XService`. В `deps` — только `db`, `time` (`TimeSource`), `config`, сервисы `platform`/`analytics` и сервисы модулей, разрешённых таблицей 7.1. Состояние модуля (реестр `GameRoom`, очередь Seek, кэши, издатель событий) живёт в замыкании фабрики. MUST NOT: синглтоны и изменяемое состояние на уровне файла модуля — два `buildApp` в одном процессе тестов не должны делить состояние.
3. **События.** `events.ts` описывает типы событий и `createXEvents()`; экземпляр создаёт фабрика сервиса и отдаёт полем `XService.events`. Подписчик получает сервис издателя в `deps` и подписывается в своей фабрике (форма событий — API §11).
4. **Межмодульные импорты** (закрывает F2-Q10). Из чужого модуля можно импортировать только `service.ts` и `events.ts`: типы (`XService`, аргументы, результаты, типы событий) и классы ошибок сервиса (`GameCreateRefused`). MUST NOT: импорт чужих `api.ts`, `repo.ts`, `tables.ts`, `domain/**` и вызов чужой `createXService` (её зовёт только `app.ts`). Общая чистая логика нескольких модулей — в `packages/*`. Правило добавляется в `.dependency-cruiser.cjs` в задаче 2 скелета.
5. **БД.** `platform/db.ts`: создание Kysely + `pg`, типы `Db` и `Trx`, `withTransaction(db, fn)`. Типы таблиц — в модуле-владельце: `src/<m>/tables.ts` (только типы) экспортирует `XTables` — имя таблицы → интерфейс строки (`GamesTable`, API §15). Общий `Database` — пересечение всех `XTables` в `apps/server/src/database.ts` (вне модулей; им пользуются `app.ts`, `test/support/`, `scripts/seed.ts`). `repo.ts` работает с `Db`/`Trx`, суженными до своих таблиц (`Kysely<XTables>`) хелпером `platform`: чужая таблица в запросе — ошибка компиляции, а не только `check-architecture.sh`. Точную форму generic выбирает разработчик задачи 2 при двух условиях: `platform` не импортирует модули; `repo` по типу видит только свои таблицы. `trx` между модулями передаётся как `Trx` первым параметром (API §11).
6. **Имена типов** (закрывает F2-Q12 в части `Game`). `Game` — только проекция протокола (`packages/protocol`, API §15). Строка БД — `GamesTable` (вставка/выборка — `Insertable<GamesTable>`/`Selectable<GamesTable>`), доменные объекты называются по роли (`ClockState`, `GameRoom`). MUST NOT: второй тип с именем `Game`, `Challenge`, `Seek` и т. п. в `apps/server`. Так же для других сущностей.
7. **«Кто» в HTTP** (закрывает F4-Q6, часть 1). `platform/http.ts` объявляет `Caller` — `{who: "guest"}` или `{who: "onboarding" | "player", user_id, session_id}` (значения — столбец «Кто» API §12: Г, П1, И) — и `CallerResolver`. `buildApp` передаёт в `platform` резолвер `auth.service.resolveCaller`; хук `onRequest` `platform` ставит `request.caller`, `registerRoute(app, REST_ROUTES.<операция>, handler)` сверяет его с `who` маршрута. До фичи `auth` (скелет) резолвер всегда возвращает гостя. `platform` об `auth` не знает.
8. **WebSocket-обработчики** (закрывает F4-Q6, часть 2). `api.ts` модуля экспортирует `registerXApi(app, svc)` (REST) и, если есть команды, `xWsHandlers(svc): WsHandlers` — объект «`type` сообщения → обработчик». Типы `WsHandlers` и `WsContext` (`caller`, id соединения, RTT) — в `platform/ws.ts`, поэтому модули не импортируют `realtime`. `app.ts` вызывает `realtime.registerHandlers(gamesWsHandlers(…), …)`; два обработчика одного `type` — ошибка при старте. `realtime` получает `auth.service.resolveCaller` через `deps` (связь `realtime` → `auth` есть в 7.1).
9. **Жизненный цикл.** Сервис может экспортировать `start()` и `stop()` (восстановление и таймеры — ADR-0007). `buildApp` вызывает `start()` по слоям в хуке `onReady` Fastify (после миграций), `stop()` — в обратном порядке в `onClose`.

## Последствия
- Каждый модуль собирается и тестируется отдельно, `buildApp` в тестах изолирован; зависимости видны в сигнатуре фабрики, `dependency-cruiser` ловит лишние.
- Новый модуль — строка в `app.ts` и в `database.ts`; без этого фабрику никто не вызовет.
- Правки документов при ближайшем apply/reopen: ARCHITECTURE §7.2 (`tables.ts`, фабрики), §7.4 (правило п.4), §13.1 (`database.ts`), §3 (строка), §16, §17 (закрыть F2-Q10, F2-Q12); API §15 (`registerXApi`, `xWsHandlers`, `realtime.registerHandlers` из `app.ts` вместо «регистрирует `realtime`»), §17 (закрыть F4-Q6; F4-Q5 закрывается кодом скелета).
