# ADR-0001. Бэкенд на Node.js + TypeScript

Статус: принято — решение человека (Ivan, утверждение F2, 2026-11-04). Заменяет прежний вариант «бэкенд на Rust» (`0001-backend-rust.md`).

## Контекст
ТЗ §6 рекомендует Node.js (NestJS) или Go. У человека было пожелание «может бекэнд на Rust». Разрабатывает и сопровождает один человек (BUSINESS D4), хостинг — один небольшой VPS (D6). Нагрузка — ≤ 100 сообщений WebSocket/с (D2), p95 хода ≤ 150 мс (ТЗ §5).

## Решение
Node.js 24 LTS + TypeScript. HTTP и WebSocket — Fastify + `@fastify/websocket`, без NestJS. БД — Kysely + `pg`. Правила — chess.js через общий `packages/chess` на сервере и клиенте. Протокол — схемы zod в `packages/protocol`. Монорепо на npm workspaces. Glicko-2 — свой модуль со сверкой по эталонным векторам. Подробно — ARCHITECTURE.md разделы 3.1, 4.1, 9, 10, 13.

## Отвергнутые альтернативы
- **Rust (axum, tokio, shakmaty).** Отверг человек. По цифрам BUSINESS.md выигрыша нет: память меньше на ≈ 0,1 ГБ на среду из 4 ГБ. Цена для одного разработчика — второй язык, два движка правил и их сверка, генерация типов, `.sqlx/`, минуты сборки в CI, async Rust.
- **Go.** Второй язык и второй движок правил; по нагрузке выигрыша нет.
- **NestJS.** DI и модули фреймворка избыточны для одного процесса и одного разработчика.

## Последствия
- Один язык и общие пакеты: правила и типы протокола на клиенте и сервере совпадают по построению.
- Один поток: долгая синхронная операция задерживает все партии. Меры: запрет тяжёлых синхронных операций и метрика задержки event loop (ARCHITECTURE.md 9.4), признак роста — раздел 15.
