Проверено по запросу, находок нет:

## 🟠 prop-1. Запись каждого запуска `scripts/ops/` в GitHub Issue и «ревью как код» для одного человека
§16, S23. Ревьюер и исполнитель — один и тот же Ivan (D4), так что «прошёл ревью» ничего не добавляет. Отметка в Issue — ручной шаг при каждом запуске. Её легко забыть, и проверить это некому. Более простая альтернатива не названа: в S23 сравнение идёт только с админ-панелью и произвольным SQL. Последствие: процедура либо будет нарушаться молча, либо станет трением для единственного сопровождающего, а агенты (F6/F8) превратят её в обязательную проверку. Варианты: (а) скрипт сам пишет строку журнала: `\echo` в файл на VPS или `INSERT` в таблицу `ops_log` в той же транзакции. Без Issue и без отдельного ревью, достаточно того, что скрипт лежит в git. Этого хватит, пока сопровождающий один. (б) Оставить Issue, но только для `delete-account` и `logout-everyone`. Вернуться к журналу в трекере — когда появится второй человек с доступом к проду.

## 🟠 prop-2. `delete-account.sql` — вторая реализация удаления аккаунта
§16 говорит: «те же шаги, что раздел 13», файлы — «вручную по выведенному списку». Сценарий §13 уже реализован в `auth.service` и использует `users.service.anonymize` и `feedback.service.anonymize`, снятие Challenge и Seek, закрытие WebSocket. SQL-копию придётся держать в синхронизации с кодом при каждой миграции `users`/`feedback`, и проверять её тестами (F6). Последствие: расхождение. Например, в коде добавили поле с ПДн, а в SQL оно осталось. Или не снят Seek, не закрыт WebSocket, остались файлы. Альтернатива не названа. Варианты: (а) CLI-точка входа в образе `app` (`node dist/ops/delete-account.js --email …`): она вызывает тот же сценарий из §13, реализация одна, тесты общие. Этого хватает всегда, пока есть монолит A1. (б) До открытой беты удаление по просьбе не делать: игрок удаляет аккаунт сам (§13), в политике (F3-Q1) указать именно этот путь.

## 🟡 prop-3. Роль `ops_ro` — отдельный секрет ради защиты одного человека от самого себя
§16, §17. Ещё один пароль: его надо создать, хранить в менеджере, менять при утечке. Альтернатива не названа. Проще: `psql -U app` с `SET default_transaction_read_only = on` в `~/.psqlrc` пользователя ssh или в скрипте чтения (`BEGIN READ ONLY`). Защита от случайной правки та же, секретом меньше. `ops_ro` стоит вернуть, когда читать прод будет кто-то, кроме Ivan.

## 🟡 prop-4. `rename-nickname.sql` — модерация, которой нет в этапе
§16. «Сменить оскорбительный ник» — это модерация, а она вне этапа (D5, BUSINESS §1.7). Варианты: (а) убрать скрипт из «первых» и написать его, когда случай произойдёт: это один `UPDATE`, его можно сделать за минуты. (б) Оставить, но сослаться на D5 как на исключение.

## 🟡 prop-5. Девять лимитов с тремя видами ключей (IP / User / соединение)
§9, S11. Лимитов требует ТЗ §5, но гранулярность выбрана «по умолчанию». В S11 альтернативой названа только Caddy, вариант «меньше лимитов» не рассмотрен. Каждый лимит — это код, тест и значение, которое придётся подбирать после нагрузочного теста. Проще: лимит REST по IP/User (`@fastify/rate-limit`), token bucket на соединение WebSocket, максимум соединений на User, ограничения размеров и отдельный лимит Feedback. Отдельные лимиты на upgrade, на сообщения WS по User и на вход Google добавлять, когда в логах появится флуд, который не держит базовый набор.

## 🟡 prop-6. Блокирующий `npm audit --audit-level=high`
§18, S27. Для одного человека это частая остановка CI из-за транзитивных уязвимостей без исправления, причём часто не применимых к проекту. Dependabot alerts уже это покрывают. Вариант: `npm audit` — только как предупреждение, блокирует `gitleaks`. Блокировку вернуть, если alerts начнут копиться без реакции.

## Вне линзы
§16 `delete-account.sql` ищет игрока «по e-mail», но e-mail хранится только при `email_verified` (S19). Для части аккаунтов найти игрока не получится (линза security/tz).
