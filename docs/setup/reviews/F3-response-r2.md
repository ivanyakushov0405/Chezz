# F3 — ответ на ревью, раунд 2

Документ: `docs/SECURITY.md` v0.3. Изменены S5, S6, S20, S30, S31; новый раздел 4.1; правки F1/F2 — только в списке F3-Q3 (сам F2 не менялся).

## security

| ID | Решение | Что сделано или почему нет |
|---|---|---|
| 🔴 sec-13 | принято | Взяты варианты (а) и (б) вместе — S31, новый раздел 4.1. Удаление идёт в три шага: (1) `POST` начала с проверкой `Origin` и Session, цель `delete` и `id` Session кладутся в `__Host-oidc` только здесь; (2) Google с `prompt=select_account` — на возврате проверяются та же Session, `sub` и ≤ 5 мин от `started_at`, удаления нет; (3) ставится cookie `__Host-del` (`SameSite=Strict`, 5 мин, привязана к Session), открывается страница подтверждения, удаляет отдельный `POST` с `Origin`. GET начала входа цель «удаление» игнорирует. MUST NOT удалять в GET; есть пример атаки через `<img>`. Новых рисков нет: каждый изменяющий шаг — POST с `Origin`, а Google требует явного клика |
| 🟠 sec-14 | принято | S30, §4: отказ, если `u.pathname` начинается с `//`; редирект — на абсолютный `u.href`; в примеры и обязательный unit-тест добавлены `/.//evil.example` и `https://evil.example` |
| 🟡 sec-15 | принято | Вариант (б): свежесть подтверждается `started_at` по часам `app` и `prompt=select_account`; `auth_time` проверяется, только если Google его прислал (§4.1 п.2). От поддержки `max_age` у Google ничего не зависит |
| 🟡 sec-16 | принято | §16: обёртка `scripts/ops/ro.sh` с `PGOPTIONS='-c default_transaction_read_only=on'`; упоминание `~/.psqlrc` убрано |
| 🟡 sec-17 | принято | §17: записан как принятый риск — код ветки на staging видит секреты staging, без этого staging бесполезен. MUST: секреты staging ничего не дают для prod, `deploy/**` и скрипт выкатки берутся из `main`, образ собирается в job без секретов (F7) |
| 🟡 sec-18 | принято | §9: WebSocket-upgrade считается в общий лимит REST 300/мин по IP/User (как в A21) |
