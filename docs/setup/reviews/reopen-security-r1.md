## 🟠 security-1. «Мерж — Ivan» технически не обеспечен: токен сессии сам сливает PR, а план выкатки prod код приложения не показывает
SECURITY S24, §17 «Защита GitHub» (MUST «мерж — Ivan»; MUST F7 O43) ↔ F7 16.1 п.1–2, 16.2, 16.3, O37. После правки F3 прямо опирается на fine-grained токен с Contents RW и Pull requests RW. По F7 16.2 этот токен лежит в окружении всего, что запускают агенты (`npm test`, `npx`, скрипты). В ruleset `main` обязательного ревью нет (16.1 п.2). Правила 16.3, как F7 сам пишет, «исполняемый код не проходит». Атака: prompt-injection или вредная зависимость в `npm test` берёт `GH_TOKEN` и через REST создаёт PR из ветки с закладкой в `apps/server/`. Проверки `check`/`e2e` проходят, тот же токен мержит PR (`PUT /pulls/:n/merge`). На следующей выкатке prod план O37 показывает diff только `deploy/`, `scripts/ops/`, `.github/`, `migrations/`. Ivan подтверждает выкатку, закладка уходит в prod и получает доступ к БД со всеми e-mail. Последствие: «мерж — Ivan» и пример в §17 описывают защиту, которой нет; агенты-разработчики будут считать `main` проверенным. Варианты: (а) в план O37 добавить список коммитов и PR между базой O41 и SHA выкатки (кто и когда смержил), а в §17 записать MUST: Ivan сверяет этот список со своими подтверждениями `gh pr merge`; (б) не держать `GH_TOKEN` в окружении процессов, которые запускают агенты: токен получает только `gh` оркестратора через обёртку, и `npm test`/`npx` идут с очищенным env; (в) записать в §17 как принятый риск со сценарием выше и правкой F7 в §20 (F3-Q3 или новый вопрос) — минимум, если (а) и (б) откладываются.

## 🟡 security-2. Cookie сид-игроков на staging, полученная через HMAC, не маскируется и никогда не меняется
TESTING V20, §7.6, §9; SECURITY §17 (таблица, `SEED_TOKEN_SECRET`). GitHub маскирует только сам секрет, а вычисленный `__Host-sid` не маскирует. Playwright по умолчанию пишет trace и отчёт с заголовками `Cookie`. В публичном репозитории артефакты и логи job `staging` скачает любой пользователь GitHub. Формула `HMAC(секрет, ник)` детерминирована, поэтому утёкшая cookie действует при каждом следующем подъёме staging, пока секрет не сменят. Атака: smoke упал, `playwright-report` загружен артефактом, посторонний берёт cookie `seed_player_01` и при следующем подъёме staging входит на него. Последствие: V20 закрывает публичный код, но не публичные артефакты. Ущерб ограничен staging с сид-данными, поэтому 🟡. Варианты: (а) в §7.6/§9 записать MUST NOT: trace, видео, `playwright-report` и вывод cookie в job `staging`; хелпер входа делает `::add-mask::` для вычисленного значения; (б) добавлять соль запуска: `HMAC(секрет, run_id ‖ ник)`, `run_id` передаётся в `up` и в шаг smoke, тогда cookie живёт один подъём.

## 🟡 security-3. `account_deleted` в journald вытесняется по размеру раньше, чем понадобится при восстановлении
SECURITY §14 (новый пункт про `account_deleted`), §15 ↔ F7 §5 (`SystemMaxUse=1G`), 14.3. Журнал общий для `app` prod, `app-staging` с кодом веток, нагрузочного теста и `edge`. При флуде, болтливой ветке на staging или нагрузке лимит в 1 ГБ вытесняет старые записи раньше 14 дней, и строки об удалениях за время после бэкапа пропадают. Скрипт 14.3 тогда молча печатает неполный список. Атака или случай: флуд по API за сутки до порчи БД → восстановление на живом VPS → удалённые аккаунты возвращаются без предупреждения (ТЗ §5 «удаление по запросу»). Варианты: (а) скрипт 14.3 проверяет, что самая ранняя запись журнала `chezz-app-1` старше времени бэкапа, иначе громко предупреждает и ведёт к процедуре S39; (б) отдельный namespace journald или файл только для `account_deleted` с собственным сроком хранения; (в) лимит `SystemMaxUse`/`RateLimit` для контейнеров staging, чтобы они не вытесняли prod.

## 🟡 security-4. Маскировка S37 перечисляет хуки, но не поля, и не трогает текст ошибок
SECURITY S37, §15 (Sentry) ↔ F7 O18. Названы только сериализатор пути `pino` и `beforeSend`/`beforeBreadcrumb`. Остаются: `event.request.url` и `event.transaction` у клиентского Sentry, `beforeSendTransaction`, если включат трассировку, сообщения исключений и `extra` вида `challenge 3f2c… expired` из `challenges.service`. Атака: читатель Sentry (или утечка проекта Sentry) находит `id` открытого вызова по ссылке и принимает его раньше друга (S9). Варианты: (а) одна функция маскировки в `platform` применяется к `request.url`, `transaction`, breadcrumbs, `message` и строкам исключений; MUST unit-тест на эти поля и MUST `beforeSendTransaction`, если включена трассировка; (б) MUST NOT: `id` вызова в тексте ошибок и `extra`, только `:id` или без него.
