# F3 — consistency, раунд 2 (весь документ)

Проверено: `docs/SECURITY.md` v0.2 целиком против F1 `GLOSSARY.md`, F2 `ARCHITECTURE.md`, `BUSINESS.md`. Внутренних 🔴 нет. Расхождения с F1/F2, которые F3-Q3 уже оговаривает, не считаются находками (список ниже).

## 🟠 consistency-1. Сценарий удаления аккаунта нарушает таблицу зависимостей F2 §7.1
§13 п.1–2: `auth.service` проверяет `active` Game, вызывает `challenges.service` и `matchmaking.service`. ARCHITECTURE §7.1: `auth` зависит только от `users`, `feedback`; §7.1 «остальные связи — только из таблицы», §7.4 проверяет это `dependency-cruiser`. Этих изменений нет в F3-Q3 (там только события и поля). Последствие: код по §13 не пройдёт CI; агент либо нарушит правило, либо решит сам. Варианты: (а) добавить в F3-Q3 правку §7.1 (`auth` → `games`, `challenges`, `matchmaking`) и проверить отсутствие цикла (`realtime` → `auth` уже есть); (б) убрать шаги из `auth`: `challenges`/`matchmaking` подписываются на событие `auth` «аккаунт удалён» (цена — не одна транзакция, S17 проверка `active` всё равно требует `games`).

## 🟠 consistency-2. S11 сокращает лимиты, заданные в F2 A21, и это не вынесено в F3-Q3
ARCHITECTURE A21: `@fastify/rate-limit` на REST и WebSocket-upgrade по IP и User; token bucket в `realtime` на соединение и на User. F3 §9/S11: лимита upgrade нет; token bucket только на соединение; лимит по User только у REST и Feedback; «сообщения по User» — по признаку. F3 ссылается на A21 как на основание. Последствие: A21 утверждён и говорит иное; агент `realtime` прочтёт две версии. Варианты: (а) добавить в F3-Q3 правку A21 («значения и набор — F3: см. §9»); (б) вернуть upgrade-лимит в базовый набор.

## 🟡 consistency-3. S6: «≈ 2,5 запроса/с» против «одним запросом» (§5)
S6 считает 150 соединений / 60 с = 2,5 запроса/с, §5 — «одним запросом проверяет Session всех соединений» (≈ 1 запрос/мин). Одно из двух неверно. Привести S6 к §5.

## 🟡 consistency-4. Уборка файлов скриншотов: S20/§14 против §13
§13 последний MUST: «ежедневная чистка удаляет файлы без строки Feedback», но п.4 оставляет строку Feedback с `screenshot_url = NULL`, так что осиротевший файл «со строкой» не определяется. S20/§14 называют автоматической чисткой только истёкшие Session и скриншоты старше 90 дней; чистка сирот — третий вид, не упомянутый. Также не сказано, что со строкой Feedback при удалении по сроку 90 дней (`screenshot_url` → NULL?). Переформулировать: «файлы, на которые не ссылается ни одна строка `feedback`», добавить в S20/§14.

## 🟡 consistency-5. Проекция «своих» данных не включает `terms_accepted_at`
§12 таблица: `settings`, `locale`, `terms_accepted_at` видны самому игроку; MUST ниже: свои поля — `email`, `settings`, `locale`. §1 запрещает отдавать `terms_accepted_at` чужого. Либо добавить поле в «своё», либо убрать «самому игроку» из таблицы.

## 🟡 consistency-6. Feedback и первый вход
§7: Feedback — «Гость да, Игрок да»; §5: Session без ника/правил — 403 на всё, кроме списка (в нём нет Feedback, S5 — тоже). Пользователь на шаге первого входа отправить отчёт не может, хотя гость может. Добавить Feedback в список разрешённого или оговорить. Заодно S5 («выход и удаление») и §5 («прочитать своё состояние, выбрать ник и принять правила») — выровнять списки.

## 🟡 consistency-7. CSP добавляет домен, которого нет в F2 §14
§6 разрешает `img-src https://lh3.googleusercontent.com`, §10 называет его единственным сторонним доменом картинок, а §6 сам требует правки ARCHITECTURE §14 для нового домена. F2 §14 перечисляет Google только как OAuth/OIDC, домена аватаров нет; в F3-Q3 пункта нет. Добавить пункт в F3-Q3 (F2 §14: «Google — аватары `lh3.googleusercontent.com`»).
