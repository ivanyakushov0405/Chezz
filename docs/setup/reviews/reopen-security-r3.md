## 🟠 security-5. O45 не замечает закладку внутри PR, который Ivan подтвердил, а в F3 §17 написано, что закладка «не попадёт в prod»
Где: F3 §17 «Принятый риск» («Закладка попадёт в `main`, но не в prod, если Ivan сверит список O45»), F7 O45, 9.2а п.1, 16.2, O36.

Почему так. Ivan сверяет номер, заголовок и время мержа. Перед `gh pr merge` он видит только diff `.github/`, `deploy/`, `scripts/ops/` (O36), а код `apps/server/` не видит.

Атака. Процесс из `npm test` с тем же `GH_TOKEN` (Contents RW) через REST добавляет коммит с закладкой в ветку PR #41. Это уже открытый PR агентов, его мерж Ivan скоро подтвердит. Или закладка просто дописывается в рабочую копию, а оркестратор коммитит её сам. Проверки проходят. Ivan подтверждает мерж #41, и в списке O45 номер, заголовок и время совпадают. Закладка уходит в prod без единого расхождения.

Атакующему этот путь проще, чем отдельный PR. Поэтому реальная защита O45 — «нет лишних PR», а не «закладка не дойдёт до prod». Вариант (б) при пересмотре закрывает только путь через токен: подмену рабочей копии он не закрывает.

Последствие: Ivan принял риск, описанный уже, чем он есть. Агенты и Ivan будут считать сверку O45 барьером от закладок в коде.

Варианты:
- (а) Оркестратор мержит только с `gh pr merge --match-head-commit <SHA, который он сам запушил>`: MUST в O36 и 16.3. Чужой коммит, добавленный в ветку после push, тогда валит мерж. Подмену рабочей копии этот вариант не закрывает.
- (б) Минимум: переписать абзац F3 §17 и O45 честно. O45 ловит PR и коммиты, которые Ivan не подтверждал, но не ловит изменённое содержимое подтверждённого PR и подмену рабочей копии кодом зависимостей. Этот остаток входит в принятый риск до этапа 5. Вариант (б) security-1 закрывает только путь через `GH_TOKEN`.

## 🟡 security-6. В 9.2а не сказано, где лежит скрипт списка; если это файл вне `.github/workflows/`, закладка прячет сама себя
Где: F7 9.2а, 9.2 (`plan`); для сравнения у `build` прямо написано «скриптов репозитория на runner не запускает».

Атака. Если агент вынесет цикл 9.2а в `scripts/ci/pr-list.sh`, токен (Contents RW, без Workflows) в том же PR с закладкой правит скрипт так, чтобы тот пропускал свой номер PR. Скрипт запускается из `main`, то есть из проверяемого кода. В diff O37 изменение попадает только при правке под `.github/`.

Варианты:
- (а) MUST: цикл 9.2а — inline `run:` в `.github/workflows/deploy.yml`, другие файлы репозитория `plan` не запускает. Изменить такой файл токен не может.
- (б) Скрипт кладётся в `.github/workflows/` и правится только Ivan.

## 🟡 security-7. Заголовок PR попадает в Markdown итога без экранирования
Где: F7 9.2а, `jq`-шаблон `\(.title)`.

Заголовок задаёт атакующий. Pull requests RW позволяет переименовать и уже смерженный PR. Атака: заголовку более раннего, легитимного PR дописывается `<!--`. GFM в `$GITHUB_STEP_SUMMARY` скрывает все строки после него, включая строку закладки и итог «PR: N, коммитов вне PR: M». Символ `|` в заголовке сдвигает колонки.

Варианты:
- (а) Экранировать `|`, `<`, `>`, `` ` `` в `title` и в `%s` коммита, например `gsub("[|<>`]"; "_")`.
- (б) Выводить список в блок кода ```` ``` ````. Плюс MUST в п.1 сверки: итоговая строка есть, и N равно числу строк.

## 🟡 security-8. При `bootstrap=true` проверка O45 пропускается целиком, хотя база может существовать
Где: F7 9.2а последний пункт, O44 (новый VPS после аварии, 14.3), 9.1.

На новом VPS после аварии успешные запуски `prod deploy` есть, и O44 сам на это указывает. Но список PR не строится, а полный diff `deploy/` и `.github/` код `apps/server/` не показывает. Атака: закладка смержена токеном, а следующая выкатка — восстановление на новый VPS под давлением аварии. Сверки нет вообще. Вероятность низкая, поэтому 🟡.

Варианты:
- (а) С `bootstrap=true` всё равно искать последний успешный `prod deploy`. Если он найден, строить список O45 от него, если нет — пометка как сейчас.
- (б) MUST в 14.3: перед `bootstrap=true` на новом VPS Ivan вручную сверяет `gh pr list --state merged --search "merged:>=<дата последней выкатки>"`.
