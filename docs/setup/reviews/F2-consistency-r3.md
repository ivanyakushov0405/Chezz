## 🟠 consistency-16. Принятие вызова не защищено от двойного принятия, отмены и истечения
Разделы 9.1 п.2–3, A25, 9.2. Команды сериализует только `GameRoom`, а комнаты у вызова нет. `challenges.service.accept` открывает транзакцию, вызывает `createGame` и ставит `accepted`. `lockForGame` блокирует только строки игроков, то есть принимающего и создателя. Проверка `Challenge.status = open` под блокировкой строки вызова нигде не описана. Последствие: два разных игрока одновременно принимают один открытый вызов. Оба проходят проверку «игрок занят», так как создатель блокируется по очереди, но у создателя уже будет `active` Game только после первого коммита. Если порядок блокировок сложится иначе, получаются две партии из одного Challenge. Те же гонки: принятие против отмены создателем и принятие против истечения (30 мин). Варианты: (а) в 9.1 п.2 добавить: `challenges/repo` читает вызов `SELECT … FOR UPDATE`, проверяет `status = open` и срок и только потом вызывает `createGame`; блокировка вызова идёт раньше блокировки игроков, и порядок зафиксирован. (б) Условный `UPDATE challenges SET status='accepted' WHERE id=… AND status='open'` первым шагом транзакции; 0 строк — отказ.

## 🟠 consistency-17. Rate limit по User в `platform` противоречит графу зависимостей
A21, 7.1 строка `platform` («Может зависеть от: —», «rate limit REST»), A20, `auth`. A21 требует лимит `@fastify/rate-limit` «по IP и User». User определяется по Session, а Session проверяет `auth`. Но `platform` ни от кого не зависит, а `auth` зависит от `users`. Последствие: либо `platform` нарушает 7.1 (и `dependency-cruiser` по 7.4 упадёт), либо лимит по User не реализуем. Варианты: (а) `platform` даёт лимит только по IP, а лимит по User регистрирует `auth` как Fastify-хук с ключом `user_id`; поправить A21 и 7.1. (б) `platform` принимает функцию ключа (`keyGenerator`), которую передаёт `main.ts`; сказать об этом в 7.1.

## 🟡 consistency-18. «Снять Seek» описано двумя механизмами
7.3, таблица: `matchmaking` подписан на событие `games` «партия началась» «(снять Seek игроков)». Пример ниже: «`matchmaking` снимает Seek обоих» после вызова `createGame`. Для подбора это один и тот же шаг. Для партии из вызова (`challenges`) снятие Seek идёт только по событию. Последствие: исполнитель может сделать снятие дважды или только в одном месте. Вариант: в примере оставить «по событию» и добавить, что при подборе Seek снимается тем же обработчиком. Либо сказать, что подбор снимает сам, а событие нужно только для партий из вызовов.

## 🟡 consistency-19. Правило имён таблиц A23 и таблица `feedback`
A23: «таблицы во множественном числе». В разделах 6.1 и 8 таблица называется `feedback`, остальные — `users`, `games`, `ratings`. `sessions`, `challenges`, `analytics_events` тоже во множественном числе. Последствие: `scripts/check-architecture.sh` (7.4) сопоставляет таблицы с модулями по таблице 8, и имя `feedback` выбивается из правила. Вариант: оставить `feedback` и добавить оговорку в A23 («`feedback` — неисчисляемое»).

## 🟡 consistency-20. Правило импортов `domain`: белый список в 7.2, чёрный в 7.4
7.2: «`domain` импортирует только `packages/chess` и собственный код». 7.4 проверяет запретный список (`kysely`, `pg`, `fastify`, `ws`). Последствие: `domain` может импортировать `zod` или `pino`, и CI это пропустит, хотя 7.2 этого не разрешает. Вариант: привести 7.4 к 7.2 (запретить всё, кроме `packages/chess` и своего модуля) или расширить правило 7.2.
