## 🟠 agent-9. Разделы 3.3 и 3.2 превышают бюджет
`section.sh --toc`: 3.3 «Наблюдаемость, бэкапы, доступ» ≈1873 ток., 3.2 «CI и выкатка» ≈1586 ток. Агенты (devops, `/release`) читают таблицу решений за обоснованием по `O#`; раздел неделим и тянет лишнее.
Последствие: каждое обращение к решению по бэкапам или доступу стоит ≈1,9k токенов.
Варианты: (а) разбить 3.3 на 3.3 (наблюдаемость) и 3.4 (бэкапы и доступ), 3.2 — на «CI» и «выкатка»; (б) перенести длинные обоснования в ADR и оставить в таблице одну строку и ссылку.

## 🟡 agent-10. Коды выхода и `result=` определены только для prod
9.3: коды 0–5 и `result=` описаны для prod. У `staging up/down/load` коды не заданы (кроме `load`: код 3 «на prod играют» в разделе 11 — это противоречит значению 3 `prod_busy`, но смысл схож). Раздел 10 ссылается на `result=` «prod/staging».
Вариант: одной строкой в 9.3: те же коды для staging, `up` провален → код 1 `up_failed`, `load` при игре на prod → код 3 `prod_busy`.

## 🟡 agent-11. Первый запуск staging до первой выкатки prod
6.1: compose вызывается с `--env-file compose.prod.env --env-file compose.staging.env`. Если staging поднимается до первой выкатки prod (раздел 4, пример TESTING §14 п.6), `compose.prod.env` ещё не существует, `APP_DOMAIN` для `edge` пуст. 9.1 порядок «prod первой» не зафиксирован MUST'ом, а в 5 «первая выкатка prod» после bootstrap — только фраза.
Вариант: MUST в 9.1/5: «первый запуск `deploy.yml` — `env=prod`; `up` staging без `compose.prod.env` → код 2», либо `bootstrap.sh` создаёт `compose.prod.env` из vars.
