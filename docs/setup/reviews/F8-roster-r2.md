## 🔴 roster-13. Задачи 1 и 2 скелета не проходят шаг 3 «Проверки»
`feature.md` этап 4 шаг 3 запускает проверки профиля с пометкой «после разработчика». Для всех задач это `check` = `npm run check`. Пропуск 8.4 / В4 касается только `infra-up` на этапе 0.
- Задача 1 `[infra]` (`compose.test.yml`): корневого `package.json` ещё нет, поэтому `npm run check` падает. devops этого не исправит: `package.json` не в его зоне.
- Задача 2 `[backend:platform]`: по TESTING §6 `check` включает `scripts/check-api-doc.sh`. Этот файл создаёт задача 3, и он в зоне `contracts`, а не `backend`. `npm run check` в задаче 2 падает на отсутствующем скрипте. backend-dev по своему правилу «файл вне зоны — блокер» вернёт задачу. Задача 3 (`contracts`) тоже не может дописать вызов в `package.json`: файл не в её зоне.

Последствие: первые две задачи первого эпика гарантированно краснеют на шаге 3 и уходят в ⛔ «лимит раундов» (k > 3). Конвейер с первой задачи не идёт, а В4 закрывает только этап 0.
Варианты: (а) в профиль, «Скелет репозитория», и в 8.4 записать, что у задачи 1 проверка после разработчика — только её самопроверка (`docker compose … up -d --wait`), без `check`. В задаче 2 `check` вызывает `check-api-doc.sh` только если файл есть (`[ -f … ] && …`); задача 3 эту оговорку не убирает, поэтому дать `contracts` ещё и `package.json` либо снимать оговорку в задаче 4 `[backend:platform]`; (б) `backend allow scripts/check-api-doc.sh`: задача 2 кладёт заглушку `exit 0` с пометкой, задача 3 её заменяет. Пишут обе роли по очереди, как с `check-architecture.sh`, плюс строка в PIPELINE_DECISIONS §2. В любом варианте В4 расширить: «этап 0 и шаг 3 задачи 1».

## 🔴 roster-14. Зона `contracts` без `package-lock.json`
`zones.conf`: зона `contracts` — это `packages/protocol/**`, `packages/chess/**`, `scripts/check-api-doc.sh`. Задача 3 скелета создаёт два новых workspace, а у них зависимости (`zod`, `chess.js`; ARCHITECTURE §10, A14). `npm install` обязательно переписывает корневой `package-lock.json`: туда попадают и сами workspace, и их зависимости. `check-zone.sh end` сравнивает дерево целиком, поэтому изменение `package-lock.json` считается нарушением. Оркестратор его откатывает, и `npm ci` в CI падает на рассинхроне lock-файла.
Последствие: задача 3 скелета не завершается. Позже то же будет с любой задачей `[contracts]`, которая добавляет зависимость.
Варианты: (а) `contracts allow package-lock.json`, как у backend и frontend: задачи идут по очереди, а PIPELINE_DECISIONS §2 уже это обосновывает; (б) задача 2 заранее создаёт `packages/protocol/package.json` и `packages/chess/package.json` с зависимостями и lock-файл. Это хуже: файлы чужой зоны, а при новой зависимости проблема повторится.

## 🟠 roster-16. Корневые конфиги нужны задачам 3 и 5, а писать их может только backend
`tsc -b` (TESTING §6) идёт от корневого `tsconfig.json`. Если в нём `references`, то ссылки на `packages/*` и `apps/web` должны появиться в задачах 3 и 5. Если задача 2 добавит их заранее, `tsc -b` упадёт на несуществующих проектах (TS6053). Компонентным тестам `apps/web` нужна среда jsdom (DESIGN §17 → F6 §5), а она задаётся в корневом `vitest.config.ts`. Правила ESLint для React (`react/no-danger`, TESTING §11) — в корневом `eslint.config.*`. Всё это зона только `backend`. Задача 2 в профиле перечисляет файлы, но не говорит, что их настраивают **с расчётом** на задачи 3 и 5.
Последствие: задача 5 `[frontend]` упирается в зону (как в roster-13). Другой исход хуже: проверка молча не охватывает `apps/web`, `check` зелёный, а типы SPA никто не проверяет.
Варианты: (а) в «Скелете», задача 2: «корневые конфиги — сразу на все workspace из ARCHITECTURE §13.1: `tsconfig` без `references` на несуществующие (через `include` или `files`), проекты Vitest с jsdom для `apps/web/**`, плагины ESLint для React и Playwright»; (б) после задачи 5 — короткая задача `[backend:platform]` «подключить web и пакеты к корневым конфигам».

## 🟠 roster-17. Smoke staging до мержа: скелет и push ветки
Профиль, раздел «Ручные проверки Ivan», п.1: «фича трогает выкатку → `deploy-staging` с `REF=feature/<slug>`». Задача 7 скелета (`Dockerfile`, `deploy.yml`) трогает выкатку. Но по O40 первая выкатка — `env=prod` с `bootstrap=true` без staging: «`up` staging без выкатки prod → код 7». Значит, ⛔ этапа 5 для скелета гарантированно упадёт с кодом 7. Кроме того, `gh workflow run --ref feature/<slug>` требует, чтобы ветка была на GitHub, а push по `feature.md` идёт на этапе 6. Ни профиль, ни 8.4 не говорят «push ветки на этапе 5», а В2 описан как блокер именно «этапа 6».
Последствие: первый эпик (если задача 7 в нём) застревает на этапе 5. В обычной фиче оркестратор либо пушит вне описанного шага, либо не может выполнить ⛔.
Варианты: (а) вынести задачу 7 в отдельный эпик «Выкатка» обязательно, а не «можно» (профиль уже это допускает), и для него записать порядок O40: мерж → Ivan `bootstrap=true` → staging; (б) в профиль и 8.4 записать: «перед `deploy-staging` из ветки — `git push -u origin feature/<slug>` с подтверждением Ivan (O36)», а в В2 исправить «блокирует первый `git push` — этап 5 или 6».
