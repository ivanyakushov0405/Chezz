## 🟠 agentability-9. Матрица 10.4 противоречит правилу `AsyncState` и сама себе
§10.1 / §7 требуют, чтобы каждый запрос экрана проходил через `AsyncState` с обязательными ветками loading / error / not_found / empty, а §10.4 говорит «экран реализует ровно эти состояния». Но у `lobby`, `game-live`, `game-spectator`, `analysis`, `leaderboard`(есть), `settings`(нет `not-found`, ок) нет `error` (у `lobby`, `game-live`, `game-spectator`, `analysis` — нет), у `game-spectator` нет `not-found`, у `game-review`/`game-live` нет `empty`, а у `challenge-new` `error` без `loading`. Разработчик, следуя типу `AsyncState`, обязан реализовать ветку, которой нет в матрице; дизайнер фрейма не нарисует; ревьюер по §17 не примет ни то ни другое. Варианты: (а) добавить недостающие `error`/`not-found` в строки; (б) явно сказать: ветки `AsyncState`, не перечисленные в строке, рисуются общим видом из 10.1 и фрейма не требуют (тогда «ровно эти» заменить на «минимум эти»).

## 🟠 agentability-10. `data-state` — одно значение, а состояния партии одновременные
§10 (шапка): ID состояния = `data-state` корня экрана в e2e. У `game-live` одновременно возможны `low-time`, `offer`, `opponent-away`, `reconnecting`, `promotion` (и `confirm-move`). Приоритета или формата (список через пробел?) нет; тест не поймёт, какое состояние проверяет. Это же касается правила «фрейм на каждое состояние» — комбинации не определены. Вариант: (а) `data-state` — список ID через пробел (`~=` селектор), порядок не важен; (б) указать приоритет и что остальные — атрибуты `data-<id>`. Плюс: ни §1, ни §17 не требуют самого `data-state` и не проверяют его наличие — добавить строку.
