# F4 — consistency, раунд 1

🔴 нет. Блокирующих противоречий не найдено; ниже 🟠 — расхождения, на которых два агента напишут разный код.

## 🟠 consistency-1. Порядок проверок противоречит примеру с `ply_mismatch`
Раздел 5.2: «участник → `game_not_active` → очередь → `ply` → допустимость». Раздел 9.2, первый пример: чёрные сходили (`ply` 12), затем «повтор того же сообщения после переподключения (`ply: 11`) → `ply_mismatch`». Но после хода очередь белых, значит по порядку 5.2 ответ — `not_your_turn`. Та же формулировка в таблице 5.2 («`ply_mismatch`: повтор хода с устаревшим `ply`») и в P22 («при `ply` безопасно»). Для `game.move` код `ply_mismatch` по порядку 5.2 почти недостижим (нужно, чтобы очередь совпала при чужом `ply`).
Последствие: тест по примеру 9.2 красный на реализации по 5.2 (или наоборот); смысл защиты S10 в тестах расходится.
Варианты: (а) поставить `ply` перед очередью (`участник → game_not_active → ply → очередь → допустимость`) и поправить пример «ход вне очереди» (там `ply` верный — останется `not_your_turn`); (б) оставить порядок, исправить пример повтора на `not_your_turn` и убрать из 5.2 и P22 утверждение, что повтор даёт `ply_mismatch`.

## 🟠 consistency-2. Кто подписывает игроков на партию после `game.started`
ARCHITECTURE §7.3, пример: «`realtime` … шлёт событие и **подписывает их на партию**». F4 8.3: подписка — команда клиента `game.subscribe`, «на соединение — одна партия», `game.started` — «личное», о подписке после него не сказано. В 12.3 пример: `game.started` обоим → `/game/<game_id>`.
Последствие: одна реализация подпишет сервер (события партии придут всем соединениям игрока, нарушая «одна партия на соединение»), другая будет ждать `game.subscribe` — в тестах подбора и принятия вызова разные последовательности.
Варианты: (а) F4: `game.started` не подписывает, клиент шлёт `game.subscribe`; добавить пункт в 15.2 (правка ARCHITECTURE §7.3 пример); (б) сервер подписывает соединения, у которых нет подписки на другую партию, — прописать в 8.3.

## 🟠 consistency-3. Коды и статусы вне закрытого набора P6 / таблицы 5.2
(1) P6 — «фиксированный набор» статусов без 503, а 12.6 `GET /api/health` отвечает `503 {"status": "db_unavailable"}` (и не в формате ошибки раздела 5, нарушая P5/правило 1 «ошибка — только формат раздела 5»).
(2) `game_not_active` с HTTP 409 используется в 12.4 (PGN), но в таблице 5.2 (колонка HTTP) его нет — он в блоке «Только WebSocket» без статуса. `ErrorCode` задаётся одним списком, агент будет искать код в 5.2 REST.
Последствие: расхождение `ErrorCode` и маппинга статусов в `api.ts`; smoke F7 зависит от 503.
Варианты: (а) добавить 503 в P6 и явно сделать `health` исключением из формата ошибки; `game_not_active` перенести в основную таблицу 5.2 (409) с пометкой «и WebSocket»; (б) `health` всегда 200 с `{"status": "db_unavailable"}`.

## 🟠 consistency-4. «Кто: все» и П1 против SECURITY §5
SECURITY §5 (первый вход): у Session без ника/правил разрешены только своё состояние, ник+правила, выход, удаление, Feedback; «остальное — 403». F4 12.1–12.6 для чтения профиля, партий, лидеров, вызова, `analytics/events` ставит «все», а легенда («Г, П1, И») не говорит, входит ли П1 в «все». При этом `logout-all` у F4 разрешён П1, в S5 — только «выйти».
Последствие: П1, открывший ссылку на вызов или профиль, по F3 получает `onboarding_required`, по F4 — данные; реализация middleware неоднозначна. Страницы `/challenge/:id`, `/game/:id` у человека в состоянии П1 (после ссылки от друга) — основной сценарий «2 клика».
Варианты: (а) определить в легенде «все = Г + П1 + И» и внести в 15.2 п.11/12 уточнение SECURITY §5 (П1 читает публичное как гость, `logout-all` разрешён); (б) оставить F3 буквально и добавить `onboarding_required` на публичные маршруты (ломает «2 клика» ТЗ §7).

## 🟠 consistency-5. Лимит 5 соединений на User / 50 на IP не имеет ответа в протоколе
SECURITY §9 и пример: «6-е соединение отклонено». В F4 нет ни кода ошибки, ни HTTP-статуса, ни close-кода для этого (8.1 п.1 — «проверяет … лимит», раздел 10 — таблица закрытий без него; 5.2 — `rate_limited` описан как запросы/сообщения).
Последствие: upgrade-ответ у реализации выбирается произвольно (429/403/закрытие 1008), клиент не знает, что делать — переподключаться по P22 бесконечно каждые 5 с.
Варианты: (а) upgrade → `429 rate_limited` с `Retry-After`, клиент после отказа не переподключается автоматически, показывает `error.rate_limited`; (б) принять upgrade и закрыть кодом 1008 с отдельной строкой в таблице раздела 10.
