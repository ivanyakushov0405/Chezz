# F2 — proportionality, раунд 1

Цифры для проверки (BUSINESS.md §1.2–1.4): 150 онлайн / 75 партий в запасе, ≤ 100 WS-сообщений/с и ≤ 20 REST/с (D2), < 1 ГБ БД (D3), один человек без дежурства (D4), один небольшой VPS (D6).

Блокирующих (🔴) нет. Деплоимых единиц с собственным хранилищем в каждой среде одна (`app` + `db`) плюс общий `edge`, то есть в пределах ориентира «2–3 на человека». Нагрузку ни одно решение не превышает на порядок. Внешние платные сервисы не введены. Отказ от Redis (A8, раздел 6.2, ADR-0002) обоснован по каждой из пяти задач ТЗ §6, и для него есть признак роста. Претензий нет.

## 🟠 prop-1. Rust обоснован памятью, но цифры раздела 5 этот довод не подтверждают
Раздел 3 A2, раздел 4.1 «Вывод» и ADR-0001 объясняют выбор Rust вместо Node.js двумя доводами: пожеланием человека и «вдвое-впятеро меньшей памятью при двух средах на одном VPS». Раздел 5 считает ≈ 1,5 ГБ из 4 ГБ. Если взять Node.js (80–150 МБ, таблица 4.1), получится ≈ 1,7–1,8 ГБ. Разница ≈ 0,2–0,3 ГБ: размер VPS не меняется, бюджет тоже. Значит, по цифрам BUSINESS.md остаётся только пожелание, а сам документ называет Node.js «проще для одного человека». Цена Rust для D4 перечислена не вся. Это два движка правил и обвязка, которая их сверяет (A15, раздел 10). Это генерация типов и проверка её актуальности в CI (A14). Это офлайн-метаданные `.sqlx/`, которые надо перегенерировать при каждой правке SQL (A18). Это минуты CI на каждую сборку при минимальном бюджете (D6, D7). Это async Rust с акторами (A9). Ни у одного из этих пунктов нет оценки.
Последствие: Ivan подтверждает Q1, думая, что Rust экономит ресурсы VPS. На деле он платит только временем разработки, а время одного человека и есть главный дефицит проекта.
Варианты: (а) Переписать A2, 4.1 «Вывод» и ADR-0001 честно: «Rust — только по желанию человека. По памяти и нагрузке выигрыша нет: +0,2–0,3 ГБ из 4 ГБ. Цена — пункты A14, A15, A18 и время сборки». (б) Простое решение — Node.js + TS (Fastify + `ws`, chess.js на сервере), запасной вариант ADR-0001 сделать основным. Его хватит до тех пор, пока процесс `app` не упрётся в одно ядро. При ≤ 100 сообщениях/с это на 1–2 порядка дальше горизонта 12 месяцев.

## 🟠 prop-2. Нет точки пересмотра Rust, и цена перехода на запасной вариант занижена
По Q1 Rust подтверждается один раз при утверждении F2. Измеримого признака, по которому от Rust отказываются, нет. ADR-0001 и A2 утверждают, что при переходе на Node.js «меняются разделы 4.1, 10, 13». На самом деле от Rust зависят и раздел 1 (Rust-типы), и A9, A14, A15, A18, A21, и раздел 7.2 (`domain` «кроме `shakmaty`», запрет `tokio` и `sqlx`), и разделы 9 и 12 (`generated/` от `ts-rs`). Чем позже выяснится, что Rust тормозит единственного разработчика, тем дороже переход. После этапа 1 переход уже означает переписать готовый код.
Последствие: решение необратимо по факту, хотя в документе записано как обратимое. Проверить его можно только тогда, когда отступать поздно.
Варианты: (а) Добавить в раздел 15 и ADR-0001 контрольную точку: в конце этапа 1 (прототип: вход, доска, партия по ссылке, часы) сравнить фактические сроки с ожиданием Ivan. Если отставание больше, например, 1,5 раза — переход на Node.js. Если нет — Rust закрепляется окончательно. (б) Исправить список затронутых разделов в A2 и ADR-0001, чтобы цена перехода была видна при ответе на Q1.

## 🟠 prop-3. staging работает постоянно, а более простой вариант «staging по требованию» не рассмотрен
В A17 названа только альтернатива «без staging», и её справедливо отвергли из-за ТЗ §6. Постоянно работающий второй набор `app` + `db` (раздел 5) удваивает то, что сопровождает один человек. Это ≈ 0,6 ГБ памяти, вторая база с миграциями, вопрос о бэкапе staging-базы (раздел 5 и F7 его не решают) и дополнительный маршрут в Caddy. Нагрузочный тест (раздел 5) всё равно идёт в часы без игроков, потому что staging делит VPS с prod.
Последствие: на «небольшом VPS» (D6) половину ресурсов и часть ручных операций постоянно занимает среда, которая нужна только во время выкатки и одного нагрузочного теста.
Варианты: (а) staging по требованию. Его поднимает CI-workflow (compose-профиль `staging`) с одноразовой БД из сида. Сначала smoke, при необходимости нагрузочный тест, потом среда гасится. Бэкап не нужен. Этого хватает, пока на staging не надо держать долгоживущие данные. Например, если закрытое тестирование этапа 5 (10–20 человек) пойдёт на staging, а не на prod. Это надо решить и записать. (б) Оставить постоянный staging, но в A17 указать (а) как отвергнутый вариант с причиной и явно записать: «staging без бэкапа, БД пересоздаётся».

## 🟡 prop-4. Кэш сессий в памяти (A20) без потребности
При ≤ 20 REST/с (D2) проверка Session по первичному ключу в PostgreSQL занимает доли миллисекунды. Кэш добавляет инвалидацию для «Выйти со всех устройств» (ТЗ §4.1) и риск, что отозванная сессия какое-то время продолжит работать. Варианты: (а) Без кэша, запрос в БД на каждый запрос и при открытии WS. Кэш вводить, когда p95 REST в пике превысит, например, 50 мс из-за проверки сессии (строка в разделе 15). (б) Оставить кэш, но в A20 задать TTL и правило инвалидации.

## 🟡 prop-5. Признак для Redis в плане роста не измеримый
Раздел 15, вторая строка: «нужна выкатка без разрыва WebSocket или нужен второй `app`». Это желание, а не метрика, хотя заголовок раздела требует «только по измеренному признаку». Варианты: (а) «Вертикальный рост исчерпан: VPS уже N vCPU, а CPU `app` > 70%». Или «выкатки рвут больше N партий в неделю при таймере переподключения 60 с». (б) Убрать «выкатку без разрыва» из признаков: при 99% доступности (ТЗ §5) и окне переподключения 60 с она не нужна.

## 🟡 prop-6. Четыре слоя обязательны для каждого модуля, включая тривиальные
Раздел 7.2 требует MUST `api → service → domain/repo` для всех девяти модулей. У `feedback` (приём формы и файла) и у `auth` своей чистой логики почти нет. Для одного разработчика это пустые файлы и прокидывание вызовов. Вариант: разрешить модулю без доменной логики обходиться без `domain`, а запрет `api → repo` оставить.

## Вне линзы
- Раздел 5: нагрузочный тест на staging при общем с prod CPU не изолирует измерение. Где запускается генератор нагрузки, тоже не сказано: если на том же VPS, он искажает результат критерия приёмки ТЗ §7. Это для F6/F7.
