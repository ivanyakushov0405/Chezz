## 🔴 roster-21. Шаг 4 «Прогон» в задаче 1 скелета не может пройти
`feature.md`, этап 4, шаг 4: tester в режиме 2 запускается после каждой задачи. По `tester.md` («Режим 2») это `npm run db:test:up` и `git fetch origin main && npm run test:affected`. По 8.4 оркестратор может запускать `affected-tests` и сам. Профиль, «Скелет», меняет только шаг 3 («её проверка») и шаг 1 («Шаг tester — только у задач 4 и 5»: из п.5 это режим 1). Про шаг 4 ни в профиле, ни в 8.4, ни в В4 ничего нет.
В задаче 1 корневого `package.json` ещё нет, поэтому оба `npm run …` падают. Отчёт красный → задача уходит к devops, k += 1, но `package.json` вне его зоны. Через три раунда k > 3 → ⛔. Это тот же класс поломки, что roster-13, только на соседнем шаге. Фраза «Шаг tester — только у 4 и 5» допускает и второе прочтение: шаг 4 пропускается везде, кроме 4 и 5. Тогда в задачах 2, 3 и 6 unit-, int- и `[contracts]`-тесты до ревью никто не прогоняет, кроме самопроверки самого разработчика.
Последствие: при буквальном чтении первый эпик встаёт на задаче 1. При втором прочтении проверку тестов задач 2 и 3 делает только их автор.
Варианты: (а) в профиль («Скелет») и в 8.4 и В4 добавить: «шаг 4 в задаче 1 пропускается, его заменяет её проверка; в задачах 2–6 — `affected-tests` как обычно»; (б) у задачи 1 — шаг 4 только как `docker compose … ps` (сервис `healthy`).

## 🟠 roster-22. Типы основы e2e проверяет только тот, кто не может их исправить
Порядок задачи 5: шаг 1 tester (пишет `tests/e2e/*` и `tests/e2e/tsconfig.json`) → `tester-tsc` → шаг 2 frontend-dev (ссылка корневого `tsconfig.json` на `tests/e2e`) → шаг 3 `check`. Пока ссылки нет, `npx tsc -b` из `tester-tsc` файлы `tests/e2e` не компилирует, и проверка проходит, даже если в них есть ошибки. После шага 2 `tsc -b` их видит, `check` краснеет, и по шагу 3 задача уходит к frontend-dev. Но у него `deny tests/**`. Путь к arbiter есть только из шага 4, не из шага 3.
Последствие: ошибка типов в `playwright.config.ts` или `screens.spec.ts` гонит задачу 5 по кругу к роли без права на файл, пока k > 3. Это та же ловушка, что `tester-untouched`: проверку нельзя исправить в зоне того, к кому она возвращается.
Варианты: (а) в задаче 5 после tester запускать `npx tsc -p tests/e2e --noEmit` (в профиль, как «проверку» шага tester; тогда `tests/e2e/tsconfig.json` не должен требовать `composite`-ссылок на ещё не существующий `apps/web`); (б) в профиле для скелета: «`check` красный только в `tests/**` → tester (режим 1, правка), не разработчику».

## 🟠 roster-25. По умолчанию для В6 скриншоты никто не выгружает, а ссылку оркестратору вставить нечем
§9 В6: скриншоты лежат «в артефакте job `e2e`», ссылку «оркестратор вставляет в PR на этапе 6». Проверено:
- шаг выгрузки артефакта (`upload-artifact` на путь `page.screenshot`) не упомянут ни в задаче 6 профиля (`ci.yml`), ни в `devops.md`, ни в TESTING §12. devops его не добавит, а `ci.yml` потом правит только Ivan;
- артефакт появляется после запуска CI, то есть **после** `gh pr create`. Чтобы дописать ссылку, нужен `gh pr edit` или `gh pr comment`, а их нет в разрешённом списке (профиль, «GitHub и подтверждения»: только `gh pr create|view|list|checks`);
- в `tester.md` нет ни `screens.spec.ts`, ни пути вывода скриншотов. Это знание есть только в профиле, задача 5.
Последствие: на первом PR с экраном (PR скелета) скриншотов в артефактах нет. Ivan сверяет вручную, то есть фактически работает альтернатива В6, а не решение по умолчанию.
Варианты: (а) в задачу 6 профиля: «job `e2e` — `actions/upload-artifact` для `tests/e2e/screens/**` (только `screens.spec.ts`, без trace)»; в тело PR — фиксированный текст «скриншоты: артефакт `screens` job `e2e` этого PR», без ссылки; в `tester.md` — `screens.spec.ts` и путь вывода; (б) разрешить `gh pr comment` (правка O-списка через F7, дольше).
