## 🟠 tz-1. Подбор со своим контролем: решение сверх ТЗ без пометки «по умолчанию», и оно бьёт по метрике ТЗ §7
Раздел 13, строка `seek.start` («пресет или свой контроль, P14»), и P14. ТЗ §4.4 п.1 говорит только «выбирает контроль времени». Подбор по произвольному контролю нигде не помечен «по умолчанию», у него нет строки P# с альтернативой. Подбор сводит только одинаковые `time_base`/`time_increment` (GLOSSARY G15). Поэтому Seek на 7+4 почти никогда не найдёт пару.
Последствие: игрок ждёт 60 с и получает `seek.suggest_challenge`. Это портит метрику «среднее время ожидания подбора ≤ 20 с» и критерий приёмки «партия через автоподбор < 1 мин» (ТЗ §7). Агент сделает в UI произвольный контроль для «Найти игру», потому что протокол его разрешает.
Варианты: (а) `seek.start` принимает только пресеты из `TIME_CONTROL_PRESETS`, остальное — `invalid_time_control`. Свой контроль остаётся только у Challenge (ТЗ §4.3 п.1). (б) Оставить свой контроль, но завести строку P# «по умолчанию» с альтернативой (а) и вопрос F4-Qn к Ivan.

## 🟡 tz-2. `rating_range` только у `type = open` — сужение ТЗ без пометки
P14. ТЗ §4.3 п.3 даёт ограничение по рейтингу для любого вызова. В источнике P14 «по умолчанию» отнесено только к нижним границам. Запрет для вызова по ссылке выглядит как требование ТЗ, хотя его там нет.
Варианты: (а) пометить эту часть «по умолчанию» с альтернативой «разрешить и у link» и причиной (друг известен заранее). (б) Разрешить `rating_range` у обоих типов.

## 🟡 tz-3. Разбор партии гостем — сверх ролей ТЗ §3 без пометки
Раздел 14, `/game/:id/analysis` без ограничения по роли. ТЗ §3 даёт разбор Игроку («разбирает свои и чужие партии»). Гостю ТЗ §3 разрешает только «видит … завершённые партии». Отдельного решения S#/P# для гостя нет. С S28 (смотреть идущую партию) это не связано.
Варианты: (а) завести строку P# «по умолчанию: гостю разбор доступен, считается в браузере, серверу не стоит ничего» и альтернативу. (б) Для гостя `/game/:id/analysis` — «Войти».

## 🟡 tz-4. Seek сбрасывается при кратком разрыве — подбор начинается с ±100 заново
P9 и раздел 10 «Seek при обрыве»: Seek снимается вместе с последним соединением. Клиент шлёт `seek.start` заново, расширение диапазона (ТЗ §4.4 п.2) и отсчёт 60 с (п.3) начинаются с нуля. При выкатке (1012) это случится у всех ждущих сразу.
Последствие: время ожидания растёт, а оно — метрика ТЗ §7. Не блокирует.
Варианты: (а) держать Seek ещё несколько секунд после закрытия последнего соединения и при `seek.start` с тем же контролем продолжать прежний (`waited_ms` не обнуляется). (б) Оставить как есть и записать в P9 как осознанную цену.

## 🟡 tz-5. В каталоге не указан источник ролей — ТЗ §3
Раздел 12, столбец «Кто» (Г / П1 / И), и раздел 8.3. Права выведены из ТЗ §3 через SECURITY §7, но ссылки `ТЗ §3` в документе нет, поэтому покрытие показывает §3 непокрытым.
Варианты: (а) в шапке раздела 12 написать «роли — ТЗ §3, права — SECURITY §7». (б) Оставить ссылку только на SECURITY §7 и согласиться с непокрытым §3.

## 🟡 tz-6. «1 активная партия» при создании вызова не закреплена
Таблица 5.2: `player_busy` описан только для «принять вызов» и `seek.start`. ТЗ §4.3 п.5 и SECURITY §7 («Создать вызов, найти игру: 1 `open` вызов и 1 `active` партия») требуют отказа и при `POST /api/challenges` во время своей партии. В 12.3 этого нет.
Варианты: (а) в 12.3 и в строке `player_busy` добавить «создать вызов при своей `active` Game». (б) Если создавать вызов во время партии можно, это решение «по умолчанию» и правка SECURITY §7 в 15.2.

## 🟡 tz-7. Фильтр истории по дате — в UTC, а не по дню игрока
Раздел 12.4: `date_from` / `date_to` задаются в UTC. ТЗ §4.9 просит фильтр «дата». Игрок в UTC+3 не найдёт партию, сыгранную в 01:00, по своей дате.
Варианты: (а) клиент переводит локальный день в границы `started_at` (ISO с временем). (б) Оставить UTC и пометить как «по умолчанию».
